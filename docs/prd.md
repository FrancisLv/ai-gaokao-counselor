## 1. 产品概述

### 1.1 背景与问题

高考志愿填报是一个**高利害、强规则、信息严重不对称**的决策场景：

- 考生与家长面对约 3000 所院校、800 个专业，以及逐年变化的招生政策；
- 传统志愿填报工具的核心假设是「用户已经知道自己要什么」，提供的是筛选器；
- 现实中 17 岁的考生和家长**最大的痛点不是「筛不出来」，而是「不知道该问什么」**——需求本身是模糊的（"想学计算机但别太理论""离家近点""好就业"），无法映射成表单字段；
- 关键规则（转专业政策、大类分流、体检限报、单科要求）散落在招生章程等非结构化文本中，传统结构化字段答不了；
- 决策结果需要解释与风险量化，而不是甩一张表格。

### 1.2 产品定位

> **让模糊的用户，经过引导式对话逐步明确需求，最终得到一份可解释、可溯源、合规的志愿填报方案。**

- 传统工具解决：明确的用户 → 高效检索；
- 本产品解决：**模糊的用户 → 逐步明确 → 可解释的方案**。

产品形态：对话式（自然语言 + 流式输出 + 关键节点人工确认）的志愿决策支持系统，最终产出「冲 / 稳 / 保」志愿表 + 带引用出处的解释报告。

### 1.3 核心产品原则（不可妥协）

1. **关键事实可验证、失败即关闭**：每条事实性结论必须按其证据类型可溯源（文档事实→原文片段、结构化事实→行/字段/版本、派生事实→输入快照+样本+算法参数版本），验证器逐条比对，不合格打回重写或剥离，验证失败不静默放行；
2. **规则硬约束由确定性代码裁决**：选科 / 单科 / 体检 / 批次等硬性规则不交给 LLM 判断；
3. **数值可解释**：位次换算与录取概率必须给出计算依据，可复现、可审计；
4. **LLM 不许算数，算法不许编话**：LLM 负责语义理解、规划与表达；确定性代码负责规则、数值与约束；
5. **宁可明确报错，也不许编造数据**：「没有可靠数据，不予推荐」是合法且必须明确表达的结论；
6. **只做决策支持，不做代填**：最终志愿由用户确认，系统禁止承诺录取。

### 1.4 AI 价值主张（为什么不是传统工具 + 皮）

| # | AI 增量价值 | 传统工具为何做不到 |
| --- | --- | --- |
| 1 | 把「人话」变成查询条件 | 模糊表述（"别太理论"）不是字段，筛选器直接卡住 |
| 2 | 模糊偏好的语义映射 | "离家近""好就业"是语义问题，不是字段匹配 |
| 3 | 非结构化知识问答（章程 / 政策 / 体检规定） | 答案在文本里，结构化字段答不了 |
| 4 | 生成式个性化解释（为何冲、为何稳、风险在哪） | 模板覆盖不了个性化权衡 |
| 5 | 多轮追问与协商式修正 | 一次性查询不支持"不想去东北""再加两个保底的" |

同时明确边界：**精确数值查询、规则过滤、数值计算保留传统做法（SQL + 规则引擎 + 领域算法），刻意不用 LLM。**

| 用户角色 | 特征 | 核心诉求 |
| --- | --- | --- |
| 考生（高三，约 17 岁） | 有兴趣倾向但表达模糊，不了解专业内涵与规则 | 被引导着问清楚自己要什么；理解每个推荐的理由 |

## 3. 产品目标与成功指标

对应架构文档设计目标 G1–G6，转化为可验收的产品指标：

| 目标 | 指标 | 验收口径 |
| --- | --- | --- |
| G1 关键事实可验证、失败即关闭 | 幻觉率、引用覆盖率、citation accuracy | golden set 端到端评测；报告中事实性陈述按三类证据（文档/结构化/派生）逐条可验证，Verifier 比对不通过即打回或剥离，不静默放行 |
| G2 规则硬约束 | 非法志愿透出率 = 0（按已实现规则） | 已实现规则（当前为选科）不符的候选必须被确定性剔除并记录原因；单科 / 体检 / 批次等规则待生产发布链路完成后纳入，未完成前不声称其透出率 = 0（见 FR-13） |
| G3 数值可解释 | 可复现率 100% | 同输入同输出；每个概率 / 位次附带计算依据与样本年份 |
| G4 时效性 | 时效命中率 | 知识走检索而非模型参数；结构化数据按省份 / 年份 / 科类硬过滤，政策文档按适用域与生效区间过滤，杜绝过期数据召回 |
| G5 成本与延迟可控 | 单会话成本、端到端 P99 | 同一 `principal + session` 跨 run 累计 token ≤ 50K、成本 ≤ $0.15（超限截断降级）；P99 可观测且有压测数据 |
| G6 可评测 | CI 回归门禁 | golden set 进 CI，recall 不许降、幻觉率不许升，不通过阻断合并 |

检索质量基线：建设 100–200 条 golden query set，度量 recall@k、MRR、citation accuracy。

## 4. 范围定义

### 4.1 V1 范围内

- **省份边界：仅覆盖湖南省新高考（3+1+2 模式）数据**（当前系统实际数据边界；架构上支持多省扩展，但不作为 V1 承诺）；
- **年份边界：仅支持 release 清单显式声明为可用的报考年及数据集组合**；缺少对应一分一段、招生计划、规则或文档覆盖时明确拒绝，不回退到其他年份；
- **批次边界：V1 仅支持本科批**；用户未提供批次时使用本科批默认值并在画像确认卡展示，其他批次明确拒绝；
- 对话式画像采集（含追问、确认、按需补问）；
- 结构化查询（分数线 / 招生计划 / 一分一段 / 选科要求）+ 非结构化 RAG（政策 / 招生章程 / 体检规定）；
- 冲 / 稳 / 保方案生成，硬约束校验，位次换算，录取概率估计，志愿表优化；
- 可解释报告（理由 + 出处 + 风险提示 + 免责声明）+ 事实校验；
- 多轮修正、断点续跑（HITL 会话恢复）、SSE 流式输出；
- 离线数据采集 / ETL / 质检、评测体系、成本治理与降级。

### 4.2 明确非目标（写死，约束范围）

- 不做通用聊天助手、不做多学科家教、不做院校排名预测；
- 不做志愿「代填」，系统只提供决策支持，最终由用户确认；
- 不采集身份证 / 手机号等直接身份标识，不做用户画像商业化；体检 / 健康等条件敏感字段按最小化 + 知情同意 + 限期保存处理（详见 §7.4），不宣称「不采集任何敏感信息」；
- 不承诺录取结果。

## 5. 核心用户旅程（端到端）

### 5.1 用户视角旅程

以「生成志愿方案」为例，用户视角的完整旅程：

1. **发起**：用户用自然语言描述情况与偏好，提交后获得流式响应通道（SSE）；
2. **被追问**：系统解析出结构化画像，缺必需项时用自然话术追问（有限轮次，可回答「不确定」）；只给分数时系统自动换算位次，不烦扰用户；
3. **确认画像**：系统推送画像卡片，用户确认或修正后继续（HITL 暂停点）；
4. **等待检索与生成**：算法（svc-algo）从确认画像生成冲 / 稳 / 保候选池并附概率与计算依据，同时并行检索政策章程作为证据；
5. **按需补问**：仅当候选中确实存在体检 / 单科 / 语种要求且用户未提供时，才补充追问对应项；
6. **收到方案**：经过候选生成（含选科过滤与概率量化）、当年规则校验、志愿表优化与可选方案自我审查后，用户收到带概率与依据的志愿表；
7. **阅读报告**：每项推荐附理由、数据出处、风险提示与免责声明；所有事实性陈述按三类证据（文档 / 结构化 / 派生）逐条校验；
8. **多轮修正**：用户可继续说「不想去东北」「再加两个保底的」，系统在会话内协商式调整；
9. **离开与回来**：中途离开可在保留期内恢复会话，断点续跑；超时则引导重新发起。

后台数据流转（用户不可见，但为验收依据）：
自然语言 → 结构化画像 → 检索证据（SQL 行 + RAG chunk）→ 带概率的候选 → 合法志愿表 → 可解释报告。每一次「变身」中的数值 / 规则 / 排序均由确定性代码接管。

### 5.2 内部端到端时序（15 步 · 目标态权威流程）

> 本节是「系统内部究竟怎么跑」的唯一权威描述（吸收自审查报告 §7）。§5.1 是用户视角，本节是服务视角，两者对应同一趟流程。

**示例输入**：「湖南，2025 年，物理类 600 分，选物理、化学、生物，偏好长沙，帮我做一份方案。」报考年由用户提供，**不是系统默认 2025**；下文只展示字段流转，不引用具体学校 / 位次 / 概率 / 数量。

**前提**：对应省·年·科·批的数据与资格规则**已发布且覆盖范围可证明**；否则进入「证据不足」或「算法预览（ALGORITHM_PREVIEW）」，**不执行正式推荐发布**。下文 `SubmitRun / ResumeRun / WatchRun / GetRun / CancelRun` 为**目标接口**（当前尚未实现，见 §8.2 与 gap-analysis）。

主链路时序（谁向谁发起）：

```text
用户 → gateway：创建任务
       gateway → orchestrator.SubmitRun：可信身份、输入、幂等键
                    → PG：持久受理并返回 session_id/run_id
用户 ← gateway：accepted、状态/事件地址
用户 → gateway：订阅 SSE
       gateway → orchestrator.WatchRun：从指定 event_seq 订阅
worker → llm-gateway.Chat：解析意图/画像
worker → PG：保存画像；缺项/待确认时创建 interrupt
用户 ← SSE：问题或画像确认卡
用户 → gateway → orchestrator.ResumeRun：回答/确认具体 interrupt
worker → algo.EstimateProb：已确认成绩/省年科批/选科
worker ← algo：分档候选全集、概率、AuditBasis
worker → 规则评估 + RAG：当年资格/规则需求、文档证据
  如需条件补问：持久中断 → 回答 → 新画像版本 → 确认 → 重算
worker → algo.OptimizeWishlist：合法候选、已确认偏好
worker → 可选 Critic：受限修订，再优化
worker → 报告生成 → 三类证据校验 → 发布门禁
worker → PG：原子保存结果、SUCCEEDED、result 事件
用户 ← SSE / GET：同一个不可变结果版本
```

15 步分解（**主责**＝该步的唯一业务写入方；失败出口即门禁）：

| 步 | 阶段 | 主责 · 谁调用谁 | 关键工作 | 失败出口 / 门禁 |
| --- | --- | --- | --- | --- |
| 1 | 接入受理 | gateway → `SubmitRun` | 校验大小/类型/鉴权/限流；核验调用方与会话归属，创建 QUEUED run；持久化**最小化后的可恢复输入**（不能只存 hash） | 未提交无 accepted；响应丢失时同幂等键查询取回原 run，不重复创建 |
| 2 | 订阅领取 | gateway → `WatchRun`；worker 领取 | 订阅端先补发 `event_seq` 之后事件再等新事件；worker 取执行权，QUEUED→RUNNING/INTAKE；保存租约+状态版本 | 订阅断开只关订阅；worker 失败由租约恢复；排队超载返回可重试，不无限积压 |
| 3 | 意图/画像解析 | orchestrator →（可选）llm-gateway `Chat(role=profile)` | 提取字段与意图；**发云模型前先脱敏/最小化**（健康信息不原样转发）；输出过运行时 schema，不猜省/年/成绩/健康 | 模型不可用→结构化表单；范围不支持→明确报错，**不静默换年份/省份** |
| 4 | 全局必要补问 | orchestrator 确定性完整性校验（LLM 仅润色问句） | 校验省·年·科·批·分数·选科；V1 本科批可使用系统默认值但必须展示确认；当前接口只有 score，**rank-only 不强转** | 最多 **6 次**实际补问仍缺→FAILED/INCOMPLETE_PROFILE，不带缺项进算法 |
| 5 | 回答/原子恢复 | gateway → `ResumeRun` | 校验所有权/中断未过期未消费/回答类型/状态·画像版本/release 有效性；原子保存回答+消费中断+转 QUEUED；worker 按检查点应用一次 | 旧 interrupt/同键异内容/并发矛盾→冲突；重复命令→原回执；EXPIRED 不恢复，建议派生新 run |
| 6 | 完整画像确认 | orchestrator PROFILE_CONFIRM 中断 | 展示实际采用的省年科批/分数/选科/软硬偏好/默认项；确认绑定 `profile_version`，修正则生成新版本重展示；可选 `RankConvert` 位次预览 | 确认期间改画像→旧确认失效；**不读 `RankConvertReply` 里不存在的控制线字段** |
| 7 | algo 生成权威候选池 | orchestrator → `algo.EstimateProb` | 传确认后的 province/year/category/batch/score/subjects + 偏好 DTO + **release 约束（由查询执行，不只写 trace）**；候选身份/概率/分档/依据全来自 algo，**Strategy 不得替换** | 缺一分一段/计划/历史、候选空→按明确业务原因处理；仅瞬时传输故障在同输入版本内有限重试，**不用旧年份兜底** |
| 8 | 当年规则 + 证据检索 | orchestrator → algo 扩展规则（待实现）+ 本地 RAG | 规则给 PASS/FAIL/UNKNOWN + 所需字段；RAG 双路检索做 RRF/Rerank；**SQL 数值结果不与 chunk 混进同一 RRF 排名** | 规则 UNKNOWN 时**不能因 RAG 没搜到就判 PASS**；文档无可靠证据→删非必要陈述或阻断该推荐 |
| 9 | 按需条件补问/回算 | orchestrator BACKFILL interrupt → `ResumeRun` | 只问当前候选确需的属性、合并同问；健康信息最小粒度；拒绝/不知道≠条件满足，相关候选保持 UNKNOWN | 新补问计入**同一 run 上限**；到上限可排除未知候选后重检，**不绕过未知规则**；无可用候选→明确无法成方案 |
| 10 | 策略/偏好/范围 | 默认确定性；可选 llm-gateway `Chat(role=strategy)` | Strategy 把自然语言偏好转为参数或组键建议；软城市偏好交效用排序；硬排除须已确认；**新偏好必须回确认** | 未知组键/篡改概率/未确认硬约束变更→拒绝；**千级候选不全塞 LLM**（存全集、模型只看受控摘要，优化仍取完整合格集） |
| 11 | 约束复核 + 优化 | orchestrator → `CheckConstraints` → `OptimizeWishlist` | CheckConstraints 复核选科并保持概率，扩展规则管其他资格；优化输入取自**服务端合格池**，不接客户端/LLM 自造候选 | 候选不足/保底不足分别表达；**不超配置上限硬凑**；保底告警不转「系统异常」也不静默隐藏 |
| 12 | 可选 Critic 有界修订 | orchestrator → llm-gateway `Chat(role=critic)` | 审查**已优化的实际方案**（非优化前候选）；输出结构化问题分硬错误/事实错误/偏好权衡/建议；硬规则仍由代码复核 | 需修订回步 10/11，**最多 2 次**，无进展即停；未解决硬错误不可发布；Critic 非最终门禁替代 |
| 13 | 报告草稿 | orchestrator 确定性模板 →（可选）`Chat(role=report)` | 只给最终结构化方案/脱敏规则结论/证据包/风险提示；模型生成解释，**不重排志愿、不改数值**；数字/名称/引用由模板绑定 | 模型失败→同输入确定性模板，但**模板也须过下一步门禁**；不因生成失败省略关键限制 |
| 14 | 三类证据校验 + 发布门禁 | orchestrator 汇总；algo/校验器查数值约束；可选 LLM 查文本蕴含 | 校验候选身份/去重/顺序、资格覆盖与 PASS、画像确认版本、release 有效性、关键数值与算法输出一致、引用存在且适用、派生结论未越界 | 仅文案问题回步 13（**最多 2 次**重写）；候选/资格错误回上游重算（消耗 run 级回算额度，**最多 2 次**）；耗尽仍有关键错误→FAILED/VALIDATION_FAILED |
| 15 | 原子发布 + 呈现 | orchestrator worker → PG；gateway 只读转交 | 短事务内再查租约/状态·画像版本/release 未撤销，保存**不可变结果版本** + 验证摘要 + SUCCEEDED + result 事件 | 事务未提交不得宣告完成；已提交但推送失败→**重放相同 result 事件，不重复生成**；避免取消与发布双成功 |

> 循环上限汇总（与 FR-16 / `build.py` 护栏一致）：补问 6 · Critic 修订 2 · 报告重写 2 · 回算 2。旁路流程（异常 / 改方案 / 政策问答 / 方案解释）见 §8.6。

## 6. 功能需求

优先级定义：P0 = V1 核心发布必须；P1 = V1 功能完整发布必须，但不阻断受控 `ALGORITHM_PREVIEW`；P2 = 后续演进。审查报告问题使用 `REVIEW-P1-* / REVIEW-P2-*` 编号，不与功能优先级混用。

### 6.1 交互与画像采集

#### FR-01 对话式画像采集（P0）

- 用户以自然语言输入，LLM 解析为结构化画像 JSON（JSON Schema 约束输出）；
- 画像字段分五类：

| 类别 | 字段 | 采集策略 |
| --- | --- | --- |
| 全局必需 | 省份 / 年份 / 科类 / 分数（位次为可推导项）/ 选科组合 | 缺任一项不能进入检索；V1 主输入为分数，仅给位次的反向换算当前不支持（见 FR-14） |
| 系统默认（需确认） | 批次 | V1 固定为本科批；缺失时填入系统默认值并在画像确认卡展示，其他批次明确拒绝 |
| 条件必需 | 体检（色觉 / 视力）、单科成绩、外语语种、性别、往届应届、户籍学籍（专项计划） | 仅当目标候选确实有该要求时按需补问 |
| 可推导 | 位次（分数 + 省 + 年 + 科类查一分一段表）、批次控制线 | 算法推导，不问用户 |
| 可选偏好 | 地域 / 预算（学费）/ 专业兴趣 / 冲稳保倾向 | 缺失不阻断，只影响排序与解释 |

- 「信息够不够」由**确定性校验函数**裁决，禁止 LLM 当闸门；追问话术可由 LLM 生成；
- 追问有轮次上限（信息补问 INTAKE 与 BACKFILL 合计最多 6 次，仅在产生新问题时计数），提供「不确定 / 跳过」出口，并为每个字段记录 `PROVIDED / UNKNOWN / DECLINED / DERIVED / DEFAULT` 状态；全局必需字段缺失或非法时不得因轮次耗尽而进入最终推荐，应结束为 INCOMPLETE_PROFILE 或转政策问答；
- 禁止做成一张大表单。

**验收标准**：必需字段缺失时 100% 触发追问；齐全时 0 次多余追问；可选偏好缺失按低置信继续，但全局必需字段缺失 / 非法时达轮次上限必须明确终止（INCOMPLETE_PROFILE）或转政策问答，不得带缺项进入个性化推荐。

#### FR-02 画像确认（HITL）（P0）

- 采集完成后进入 PROFILE_CONFIRM 暂停点，通过 SSE 推送画像卡片；
- 用户可确认或修正，修正后从检查点续跑。

**验收标准**：未经用户确认不进入检索阶段；修正后的字段准确反映到下游。

#### FR-03 条件必需项按需补问（P0）

- 检索得到候选后，检查候选是否含体检 / 单科 / 语种等要求且用户尚未提供；
- 有则发起 BACKFILL_ASK 追问（interrupt/resume），答完回到画像确认；无则直接继续；
- 用户拒绝或「不知道」不等于条件满足，相关候选保持 UNKNOWN（可由用户选择排除），不得据此放行；补问计入同一 run 的补问上限（见 FR-01）。

**验收标准**：候选无相应要求时不追问；有要求且缺失时必追问；该类字段是约束层硬输入，缺失或 UNKNOWN 不得放行非法志愿。

#### FR-04 多轮修正与协商式探索（P1）

- 支持在已有方案基础上追加约束或调整（如排除地域、增加保底数量、询问专业内涵）；每次修订创建新 run（REVISE_PLAN），记录父结果版本，原结果保持不变；
- **首版采用保守策略：画像一变，全部下游产物（位次 / 候选 / 规则 / 证据 / 优化 / 报告）失效并重算**；仅软偏好变化的精细增量复用为后续演进（需先实现依赖追踪与回归测试），不作为 V1 承诺。

#### FR-05 SSE 流式输出（P0）

- 全链路进度与生成内容通过 SSE 流式推送；每 15s 心跳（心跳不写业务事件、不推进图）；
- **SSE 只是可断开的订阅，不承担任务生命周期**：事件先存后通知，带 run 内单调递增 `event_seq`，支持按 `Last-Event-ID` 断点续订；断网 / gateway 重启由 worker 独立完成 run，另有状态 / 结果查询（GET）与显式取消作为后备；未验证 token 不作为最终答案推送；
- 反向代理不得缓冲 SSE（部署约束）。

### 6.2 会话生命周期与恢复

#### FR-06 任务状态机与超时管理（P0）

会话（session）是容器，可含多个任务；每次方案生成 / 修订创建一个 **run**，run 内一次人工中断为 **interrupt**。恢复与幂等以 run + interrupt 为单位，不以 session 为单位（否则会吞掉同一会话内合法的第二次回答）。

run 生命周期状态：

| 状态 | 含义 | 超时 / 过期策略 |
| --- | --- | --- |
| QUEUED | 已受理待领取 | 排队单独计时并设容量保护，不混作模型耗时 |
| RUNNING | worker 执行中 | 主动执行累计上限 10min（含工具调用 / 重试 / 退避，不含人工等待）；模型单次尝试 30s 且不超剩余时限 |
| WAITING_HITL | 暂停等用户确认 / 补问 | 单次人工等待保留 30 分钟，超时转 EXPIRED |
| EXPIRED | 人工等待超时 | 过期的是 run（非会话）；检查点暂留 7 天供排查 / 复制已授权输入，不原地恢复，可在同 session 派生新 run |
| SUCCEEDED | 验证并发布成功 | 结果默认保留 30 天并支持用户提前删除，不默认永久；检查点 30 天后归档 |
| FAILED | 不可恢复错误 / 执行超时 | 检查点保留 7 天供排查 |
| CANCELLED | 用户显式取消 | 与 SUCCEEDED/FAILED/EXPIRED 同为终态，查看不改变；取消与发布双成功由状态版本条件提交裁决 |

- 另有 `stage` 记录节点阶段（INTAKE / PROFILE_CONFIRM / CANDIDATES / RULES / OPTIMIZE / REPORT / VERIFY），不新增同名微服务；循环计数保存在 run 中，画像修正或进程恢复不清零；
- 恢复入口：`POST /v1/runs/{run_id}:resume`，携带 `run_id + interrupt_id + expected_state_version + Idempotency-Key`（确认再绑 `profile_version`）；同一 interrupt 只能被一个合法命令消费一次，同键同内容返回原回执、同键异内容或旧状态返回冲突；
- **每次 resume 都校验 run 绑定的数据发布清单（release）是否仍有效**，撤销则阻断并提示新建修订 run；不设「超过 1 小时才校验」的宽限；
- 定时清理过期检查点与 Redis key（Redis 仅作可重建投影）。

**验收标准**：进程重启后 run 可精确续跑；双击 / 多标签页不同回答只推进一次且冲突被拒，下一次合法中断仍可受理；过期或已撤销 release 的数据不被直接使用。

#### FR-07 幂等与断点续跑（P0）

- 请求携带 Idempotency-Key；节点粒度幂等（按稳定操作 ID 记录副作用），重试不产生重复写库或外部调用；
- run 由带租约与 fencing epoch 的单执行者推进，关键提交校验执行权与状态版本；旧 worker 租约失效后即使收到迟到响应也不能覆盖新执行者结果或发布终态；
- 每步状态快照落库（检查点）；run 记录生命周期与执行权，检查点记录图进度，两者关联但不混为一个概念；Redis 仅作可重建投影。

### 6.3 检索与知识

#### FR-08 结构化 / 非结构化分流检索（P0）

- **强结构化数据（分数线、招生计划、选科要求、一分一段）只走 SQL 精确查询，绝不走 RAG**；
- 非结构化文本（政策 / 章程 / 体检规定）走 RAG：向量（pgvector）‖ 关键词（pg_trgm）双路 → RRF 融合 → 可选 cross-encoder 重排 → Top-K；V1 不以 `tsvector / zhparser` 为前置条件（见 ADR-0001）；
- 结构化招生数据的省份 / 年份 / 科类 / 批次必须作为**硬过滤条件**（WHERE），不是排序因素；政策文档按适用省范围、科类范围、生效区间和文档类型过滤，不得用“年份不等”误删全国政策或长期有效条款；
- 每条 chunk 携带 `source_uri + 抓取时间 + 生效区间 + 适用域 + release_id`，供引用与验证器比对；
- SQL 全参数化；RAG 文档内容视为数据而非指令（防 prompt 注入）。

**验收标准**：数值类问题的答案全部来自 SQL 行；golden query set 上 recall@k / MRR 达标且回归不下降；无跨省 / 跨年错误召回。

#### FR-09 非结构化知识问答（P1）

- 支持「这个学校转专业政策」「大类招生怎么分流」「保研率多少」类问题，答案基于检索到的章程条款并附出处；
- 走独立子图路由（`POLICY_QA / GENERATE_PLAN / EXPLAIN_RESULT / REVISE_PLAN`）：政策问答仅收适用性必要信息（学校 / 报考年 / 适用范围），不强制全套画像与成绩；问答结论不自动推导「你有资格报考」，升级为个性化资格判断须切换生成 / 资格流程并补齐必要信息；解释已有结果绑定既有 result_version、不自动重跑推荐。

#### FR-10 离线数据采集与索引管线（P0）

- 数据源：省考试院 / 阳光高考 / 院校官网；记录来源与抓取时间；
- 管线：采集 → 解析（HTML/PDF → 文本 + 表格）→ 归一化（省 / 年 / 科类 / 批次 / 专业代码）→ 分流 → 切分 → 元数据抽取 → 双写（关系表 + pgvector + pg_trgm）→ 质检；
- 切分策略：政策按条款切分，保留父级标题路径，块 300–600 字，重叠 15%；表格转 KV 文本并保留 table_id 回溯；原始文件入对象存储供溯源；
- V1 关键词检索使用 `pg_trgm`，接受长句中文关键词路的已知局限；只有 golden set 证明关键词路成为召回瓶颈后，才复评 zhparser / pg_jieba / pg_bigm（见 ADR-0001）。

#### FR-11 ETL 四层质检防线（P0）

| 层级 | 检查 | 失败处理 |
| --- | --- | --- |
| L1 格式 | 必填非空、类型正确、枚举合法 | 拒绝入库，记 etl_error_log 并告警 |
| L2 范围 | 分数 0~750、位次 1~总人数、计划 ≥ 0、录取线 ≥ 批次线 | 拒绝入库，标记待人工复核 |
| L3 趋势 | 位次年际波动 < 30%；计划突变 > 50% 告警 | 允许入库但标 needs_review，推荐时降置信 |
| L4 抽检 | 每批随机抽 5% 人工比对原件 | 错误率 > 1% 整批打回重做 |

- 每轮 ETL 记录 `etl_run_id` 与质检报告（JSON），数据可回溯到具体入库轮次。

### 6.4 方案生成与领域算法

#### FR-12 冲 / 稳 / 保方案生成（P0）

- 候选池由 `svc-algo.EstimateProb` 从已确认画像生成整池（分数 → 位次 → 候选 → 选科过滤 → 概率 → 冲稳保分档），每项携带概率与计算依据 `AuditBasis`；
- StrategyAgent 仅把自然语言偏好转为**排序 / 筛选参数或组键选择建议**，不得新增或替换候选身份、不得改写概率（候选身份与概率事实归 algo 所有）；
- 候选以**院校专业组**为单位（湖南省平行志愿投档单位）；当年招生计划与当年规则决定候选是否存在及是否可报，历史录取数据只用于概率估计；跨年组内专业变化必须标记可比性，无法可靠估计的新组单列「无可靠估计」清单，不伪造概率送入优化。

#### FR-13 硬约束校验（P0）

- 确定性规则引擎（规则表驱动）过滤：选科不符、单科不达标、体检限报、性别限制、批次错配、学费上限；
- **实现状态**：`EvaluateEligibility` 已实现 release-bound 规则版本、受限表达式、覆盖声明、专业五态与组级 `PASS_PARTIAL`；RunLifecycle 只把 PASS/PASS_PARTIAL 组送入优化，UNKNOWN/MISSING/BLOCKED/PARTIAL 不得进入 `V1_FORMAL`。旧 `CheckConstraints` 仅保留兼容；真实规则内容与覆盖范围仍须由发布链路逐类型证明，不能因接口存在而声称所有维度透出率 = 0；
- 规则判定至少区分 `PASS / FAIL / UNKNOWN`，UNKNOWN 另带原因（用户字段缺失 / 规则覆盖不足 / 条款冲突），未知不得当通过放行；
- 剔除必须记录原因，可审计。

**验收标准**：已实现规则（选科）非法候选透出率 = 0；每条剔除有明确规则依据；缺规则覆盖或存在冲突时不得发布「资格已通过」的方案，可展示待核实资料但不混入已通过候选。

#### FR-14 位次换算（P0）

- 分数 → 位次换算（一分一段表查表 + 插值）；跨年位次可比化（同位次法 / 线差法）；
- **V1 仅支持分数 → 位次正向换算**；位次 → 分数的反向换算当前无接口，只给位次的请求须明确告知能力边界，不得反推分数；
- 输出必须附计算依据。

#### FR-15 录取概率估计（P0）

- 现行方法为**加权命中率法**（`weighted_hit`，详见 algorithms.md）；早期的分位数 / 核密度为已废弃设计，不作为 V1 承诺；
- 输出概率 + 依据样本年份；数值由算法给出，人话解释由 LLM 撰写；`slip_rate`、`expected_satisfaction` 为独立性假设下的近似估计，非校准概率，不得表述为录取保证；
- 置信区间 / 不确定度表达当前无可调用接口，列为 **P2（可选）**，不在 V1 P0 范围；
- 可复现：同输入同输出（数据与算法参数版本一并固定）。

#### FR-16 方案自我挑战（Critic 循环）（P1）

- CriticAgent 审查**已优化的实际方案**（非仅优化前候选）的梯度合理性、偏好冲突、遗漏限制，返回结构化问题清单（区分硬错误 / 事实错误 / 偏好权衡 / 一般建议）；
- 有问题时携带意见回到方案生成，**Critic 方案修订最多 2 次**；轮次上限与「无进展」检测由确定性代码裁决，防死循环与 token 爆炸；
- 硬规则仍由代码复核，Critic 不定罪或豁免；未解决硬错误不可发布，仅软偏好争议可保留当前已验证方案并说明。

#### FR-17 志愿表优化（P0）

- 平行志愿规则下约束满足 + 排序优化：冲稳保配比、梯度平滑、避免同位次扎堆、保底硬下限；
- （P2）投档模拟：按「分数优先、遵循志愿」模拟投档验证方案可行性。

#### FR-18 报告生成（P0）

- 输出方案说明 + 每项理由 + 数据出处 + 风险提示 + **强制免责声明**；
- 禁止任何「保证录取」表述。

#### FR-19 事实校验（Verifier 循环）（P0）

- 按**三类证据**分别校验：文档事实 → 绑定原文片段（对象存储原件）；结构化事实 → 绑定行身份 / 字段 / 版本；派生事实（概率、效用等）→ 绑定输入快照 + 有效样本 + 算法与参数版本 + 输出，用确定性重算或一致性比较，不与章程原文硬比；
- 数字优先由结构化模板渲染并做确定性比较，LLM 仅辅助文本蕴含检查；
- 不一致打回重写（报告重写最多 2 次）；候选 / 资格错误回上游重算（消耗 run 级回算额度，最多 2 次），不靠改措辞掩盖；
- 打回超限：剥离无法验证的段落，仅输出可溯源内容并显式提示。

**验收标准**：最终报告中事实性陈述 100% 通过对应类型证据比对或被剥离；数值 / 单位被改写、引用指向错误条款、样本年份不一致时校验必须能单独报错；校验失败不静默放行。

### 6.5 平台治理

#### FR-20 LLM 治理与成本闸门（P0）

- 按角色路由模型（profile/strategy/critic/report/verify → 不同档位模型；embed/rerank 走本地模型）；角色、模型、token 上限由服务端白名单限制；
- prompt_hash 级结果缓存；**缓存 key 携带不可变 `release_id`（数据发布清单版本，含计划 / 历史 / 一分一段 / 规则 / 文档索引 / 模型算法配置）**，而非松散 data_version；ETL 发布新版本后旧缓存自然失效，run 绑定 release 后各读取端按版本选数据，禁止原地覆盖；
- Budget Guard：同一 `principal + session` 生命周期内跨 run 累计 token ≤ 50K、成本 ≤ $0.15；修订或重试创建新 run 不重置额度。每次 llm-gateway 调用前按模型价格与输入 / 输出上限**原子预占**、完成后结算（防并行调用同时查余额导致超支），超限截断后续循环并按 FR-22 降级；
- 用 `logical_call_id` 标识一次语义调用、`attempt_id` 标识供应商尝试；超时未决预占保留对账，不立即释放后重复请求；每次调用记录 token / 成本 / 延迟（llm_call_log）；
- 早期 Python 直连模型阶段只能标为「无完整治理的实验链路」，不作为正式保障（见 §8 与 `REVIEW-P1-12`）。

#### FR-21 限流与并发保护（P0）

- 按用户 / 租户令牌桶限流；网关并发闸门，超限返回排队而非 500；
- 公网部署必须限流 + Budget Guard（防止对外暴露可烧预算的接口）。

#### FR-22 降级与故障处理（P0）

| 故障 | 降级策略 |
| --- | --- |
| LLM 超时 / 限流 | 节点级重试（指数退避）→ 换备用模型 → 规则模板兜底并标注「生成质量降级」 |
| 检索无结果 | 重写查询、调整检索通道或提升 top_k，但**不得放宽省 / 年 / 科 / 批次及政策适用域**；仍不足则明确告知「无可靠数据，不予推荐」 |
| Critic 不收敛 | 若仅存在软偏好争议，保留当前**已通过门禁**的方案并标注问题；仍存在硬错误或事实错误时失败，不输出“当前最优” |
| Verify 打回超限 | 剥离无法验证的段落，仅输出可溯源内容 + 提示；剥离后无有效方案时明确失败 |
| 成本超预算 | 截断后续循环；仅可返回同一画像、同一 release 下此前已通过完整门禁的不可变结果，否则明确失败 |
| 下游服务不可用 | 熔断 + 回放同输入、同 release 的已验证缓存；无可用缓存则明确失败，不假装成功 |

#### FR-23 评测与发布门禁（P0）

- golden set（检索 + 端到端）进 CI：recall 不许降、幻觉率不许升、P99 不许超阈值，不通过阻断合并并输出 diff 报告；
- 四层测试：L1 单元（算法 / 校验函数）→ L2 proto 契约兼容 → L3 单服务集成 → L4 端到端评测；
- 每次评测记录 eval_run（git_sha + metrics）。

#### FR-24 可观测（P1）

- trace_id 贯穿 Go ↔ Python 全链路（OTel）；
- 面板指标：QPS、端到端 P50/P99、各节点耗时、错误率、重试率、单会话 token / 成本、缓存命中率、循环轮次分布、幻觉率。

## 8. 技术架构约束与收口（目标态权威）

### 8.1 架构约束前提

本节只冻结跨服务架构约束；详细 runtime schema、proto 草案、状态转换和错误码由后续派生规格定义，不在 PRD 正文重复实现细节。

- **四服务单向 DAG**：`客户端 → svc-gateway(Go) → svc-orchestrator(Python/LangGraph) → { svc-llm-gateway(Go), svc-algo(Go) }`，下游不回调上游；
- **编排用 LangGraph**（图 / 检查点 / interrupt-resume / 子图），不自研编排引擎；差异化投入在检索质量、验证器、评测、成本治理、领域算法；
- **图控制权归 orchestrator**：图的下一步、条件补问、Critic 回边统一由 orchestrator 裁决；algo 返回规则 / 数值，llm-gateway 返回预算允许 / 拒绝，gateway 只转交命令与事件、不判断图内业务；
- **存储**：PostgreSQL 承载关系表 + pgvector + pg_trgm，并配合 Redis + 对象存储；V1 不以 tsvector 分词为前置条件（见 ADR-0001）；亿级向量或高 QPS 才考虑专用向量库；
- **契约**：单一 proto 事实来源（api/ 目录），Go/Python 双端生成，跨服务数据结构定义为 proto message；
- **确定性算法在 svc-algo（Go）**：位次 / 概率 / 规则 / 优化 / 模拟，与 LLM 分离，独立测试与审计；
- **LLM 调用路径分阶段**：代码结构按「经 svc-llm-gateway」预留，早期里程碑（可靠任务底座 / 算法最小闭环阶段）运行时允许 Python 直连模型快速验证，但此阶段显式标注为「无完整治理的实验链路」、不作为正式保障；模型治理阶段（M5·E）收口为网关前置闸门（LLM 调用路径 A/B 决策点，见 ADR-0003）。接真实付费流量前必须先具备最低预算预占、隐私脱敏与调用账本能力，不因里程碑顺序把治理延后。

### 8.2 接口契约收口（HTTP / gRPC）

> 下面是**目标命名**，不是已有路由（当前 gateway/orchestrator 入口仍是 TODO，见 gap-analysis）。保留 `/v1/plans` 作兼容创建入口；旧 `profile:confirm/backfill` 作为适配器转为**同一恢复命令**，不得各自再实现一套状态机。

| 对外入口（目标） | 内部 RPC（目标） | 关键语义 |
| --- | --- | --- |
| `POST /v1/plans` | `SubmitRun` | 支持 task_kind、session、父结果引用与输入；持久受理返回 run |
| `POST /v1/runs/{run_id}:resume` | `ResumeRun` | interrupt_id、expected_state_version、profile_version、强类型回答、幂等键 |
| `GET /v1/runs/{run_id}` | `GetRun` | 生命周期、阶段、当前中断摘要、状态版本、错误及结果引用 |
| `GET /v1/runs/{run_id}/events` | `WatchRun` | SSE/gRPC 服务端流；按游标补发和等待，**不启动图** |
| `GET /v1/runs/{run_id}/result` | `GetRun` 结果读取 | 未完成返回明确状态；完成读取该 run 的不可变结果 |
| `POST /v1/runs/{run_id}:cancel` | `CancelRun` | 幂等取消，终态保持稳定 |

- 命令回复只是「已受理」，不是「已执行完成」；所有查询/订阅/结果/取消都必须验证归属，`Trace.session_id` **不是鉴权凭证**；浏览器 SSE 用受控会话认证，长期令牌不进可记录 URL。
- **事件公共字段**：`run_id / event_seq / type / stage / state_version / occurred_at / payload_version`；payload 用 protobuf `oneof` 或有版本的运行时 schema（progress / interrupt / result / error）。当前 `GraphEvent` 只有 node/type/payload_json，缺这些恢复语义。
- **恢复回答**区分 `AnswerFields / ConfirmProfile / RejectOrEditProfile / DeclineFields`；问句人类文案与字段 key 分开，不靠自由文本猜用户在确认还是改分数。
- 客户端按 `event_seq` 去重；有缺口先补读，游标超保留窗口返回「需重新同步」→ 客户端 GET 当前状态；关闭 SSE 不保证收到终态，**GET 始终可用**。
- **llm-gateway 契约**需补逻辑调用身份、预算作用域、prompt/schema/model 配置版本，以及流结束的 usage/cost/finish_reason/error；角色/模型/token 上限由服务端白名单限制；缓存命中可不增供应商费用但仍记逻辑调用与本地处理成本。
- **algo 契约**演进需显式增加版本选择、资格扩展输入与 PASS/FAIL/UNKNOWN/所需字段（现有 `CheckConstraints` 缺报考年、健康等，不能承接完整规则）；改 proto 时同步两端生成 + 契约测试。

### 8.3 服务职责与数据所有权

四个服务 + 两个内部模块，**收紧各自职责**（「Session 服务 / Verifier / Budget Guard」是内部模块，不自动意味着新增网络服务；执行 worker 可为 orchestrator 的独立进程角色，仍归同一业务服务）：

| 服务 / 模块 | 应负责 | 不应负责 | 状态与数据责任 |
| --- | --- | --- | --- |
| svc-gateway | 用户身份、访问控制、入口限流、协议校验、命令转交、SSE/查询呈现 | 解析候选资格、判断图下一节点、Critic 回边、决定放过验证 | 拥有接入身份上下文；会话与 run 业务状态**以 orchestrator 为准** |
| svc-orchestrator | 意图路由、完整画像、LangGraph、补问/确认、图重试、候选与证据组织、报告与发布门禁 | 自行编造概率、另写一套候选 SQL 口径、绕过预算直连供应商 | 会话画像版本、run、interrupt、检查点、候选快照、证据包、结果、事件的**唯一业务写入方** |
| svc-algo | 位次、候选池、确定性规则、概率、效用与优化；后续承接扩展资格规则 | 文本追问、对话状态、云模型调用、SSE | 读取已发布结构化数据/规则；返回可复核算法产物，**不推进 run** |
| svc-llm-gateway | 模型白名单、角色路由、调用前预算、缓存、供应商重试、调用账本 | 决定用户资格、图的下一步、回调 orchestrator | 预算预占与结算账本的**唯一写入方**；向编排返回结构化结果与使用量 |
| orchestrator 内 RAG 模块 | 适用范围过滤、文档双路检索、融合、重排、证据定位 | 把未召回当「无限制」、用文本检索替代数值查询 | 读取已发布文档索引；保存当前 run 的证据引用 |
| 离线 ETL / 审核模块 | 抓取/导入、清洗、身份映射、规则审核、切分/索引、质量验证、版本发布 | 在线请求中批量导入、直接覆盖正在使用的发布版本 | 公共资料与规则的写入方；通过发布清单交付在线只读数据 |

调用方向（DAG，LangGraph 内部允许有界循环，两者不矛盾）：

```text
客户端 ──HTTP 命令/查询、SSE──> gateway
                                   └──gRPC──> orchestrator
                                                ├──gRPC──> algo ──读──> 发布数据/规则
                                                ├──gRPC──> llm-gateway ──> 模型供应商
                                                ├──本地──> RAG / Embedding / Rerank
                                                └──读写──> run / 状态 / 证据 / 结果 / 事件
离线 ETL / 规则审核 ──发布──> PostgreSQL 中的不可变版本与索引
```

- gateway 主动订阅 orchestrator 事件，事件经既有响应流返回，**不需 orchestrator 反向 RPC 回调 gateway**。
- 初期共用一个 PostgreSQL 可接受，但**业务表写入权必须清楚**：不要让 gateway、worker 同时覆盖 `chat_session.status/profile`。
- 本地 Embedding/Rerank 有 CPU/GPU/内存/加载成本：从异步 RPC 事件循环移入有界执行池，离线索引与在线推理**隔离资源**。
- Go/Python 是当前工程选择，不是「只有 Go 能治理、只有 Python 能编排」的定律。

### 8.4 真实表映射与新增持久化责任

| 原文概念 | 当前仓库事实 | 收口建议 |
| --- | --- | --- |
| college | `university` | 统一 school_id / 招生代码 / 数据库 ID 映射，**不用学校名称作全局主键** |
| admission_score | `major_admission`、`school_admission` | 分专业录取与组投档数据；注明概率当前实际使用的来源与口径 |
| score_rank_map.track/rank | `category`、`cumulative_count` 等 | 文档/API 映射与真实列一致，说明批次与百分位分母 |
| policy_doc/policy_chunk | schema 曾为 `charter_doc/charter_chunk`（孤儿空表） | **已定案收口到 `policy_*`（活表）、废弃 `charter_*`**（见 ADR-0006）；支持一般政策时显式扩展文档类型与适用范围 |
| Session | `chat_session` | 保留会话容器；**run 承接一次执行**，禁止一个 status 同时表示会话和任务 |
| LangGraph saver | 自定义 `plan_checkpoint` | **已定案用官方 `langgraph-checkpoint-postgres`**（见 ADR-0002），`plan_checkpoint` 降级为审计快照 |
| data_version | 仅版本登记字段（可变 SERIAL） | **已定案改为内容哈希不可变 `release` 表**（见 ADR-0004）；各查询选到对应版本，不只加缓存键 |
| LLM 记账 | `llm_call_log` | 扩展预占、结算、逻辑调用与供应商尝试，**不依赖 token_used 事后累加** |

- 需新增/扩展的逻辑记录：run、interrupt、命令幂等回执、执行租约、事件/outbox、画像版本、artifact/结果、数据发布清单、规则及审核记录、模型预占与 attempt 账本——**可在现有 PostgreSQL 实现，不意味每项都要一个服务**。
- 当前部分招生表唯一约束未含 province、major 基础表无年/省适用域：**湖南单省内明确边界，扩省前必须核对身份与唯一键**，不得直接复用现有键宣称支持全国。

### 8.5 三类证据包与离线发布流程

三类证据（替代「每条结论溯源到原文」的旧表述，见 FR-19）：

| 类型 | 至少保存 | 如何验证 |
| --- | --- | --- |
| 文档事实 | 文档/片段 ID、标题、来源、适用范围、生效区间、原文摘录/位置、内容摘要、release | 引用存在且未变、适用性匹配、原文支持陈述；语义无法确定则标**待核实** |
| 结构化事实 | 表/数据集、业务键、字段、值、单位、来源年份、release | 与同版本权威行/快照**逐字段比较**，不让模型口算或补值 |
| 算法派生事实 | 输入与候选快照、有效样本、方法、配置/代码版本、输出、假设及告警 | 确定性重算或与已保存输出一致性比较；核验展示精度，**不与章程原文硬比概率** |

- `AuditBasis` 是现有基础、**不是完整证据包**：还需实际数据发布版本、配置、有效样本与输入输出身份。「可复现」须同时固定数据与算法参数，仅记方法名或当前 Git 分支不够。

离线发布流程（在线 run 只读绑定已发布 release）：

```text
原始公共资料
 → 暂存导入及来源/身份映射
 → 结构化质量检查、异常与跨年组变更识别
 → 条款抽取（可辅助）→ 规则人工审核/冲突处理
 → 切分、Embedding、关键词索引、检索评测
 → 结构化/规则/索引覆盖及回归全部通过
 → 原子发布 release 清单
 → 在线 run 绑定并只读；严重错误撤销对应 release
```

- 给数据/规则/索引**实际加入版本维度或不可变快照**，让每条查询选到对应版本；只在 session 存一个整数无效；**不把数据库事务跨越 HITL 长时间保持打开**；普通新版本不自动破坏旧运行，安全撤销则阻断旧版继续发布。
- 文档检索需按 ADR-0001 验证 `pgvector + pg_trgm` 的实际召回质量；`tsvector` 分词仅作为后续复评候选，不是 V1 已完成能力。Embedding 与索引必须记录模型/维度版本，换模型不能复用不兼容向量；**检索文档按不可信数据处理**，其中指令不能覆盖系统规则、授予工具权限或更改预算。

### 8.6 旁路流程（异常 / 改方案 / 政策问答 / 方案解释）

**常见异常与处理责任**：

| 场景 | 责任方与处理 | 明确禁止 |
| --- | --- | --- |
| SSE 断网/刷新 | gateway 重建订阅，从 `Last-Event-ID` 序号继续；GET 后备 | 因重连重新 SubmitRun、把断线等同取消 |
| gateway 重启 | 已受理 run 继续；新 gateway 重鉴权后读状态/事件 | 依赖原 gateway 才能落最终结果 |
| worker 崩溃 | orchestrator 租约到期接管，依检查点/命令/账本恢复 | 两个执行者同时覆盖同一 run |
| HITL 双击 | 原子消费中断、幂等回执；同键异内容返回冲突 | 按整个 session 永久去重 |
| resume 响应丢失 | 同键重试得原回执，查 run 当前状态 | 新造回答操作导致重复注入 |
| 模型 429/暂不可用 | llm-gateway 统一有限尝试、退避与预算；上层复查同一逻辑调用 | 图/RPC/SDK 各自无限重试 |
| 模型超时且用量未知 | 保留未决预占、查询/对账；有预算且策略允许才新尝试 | 断言未调用成功所以一定不计费 |
| algo 参数非法/数据缺失 | orchestrator 提示修正或失败，用结构化原因 | 换年份/省份、重试确定性非法输入 |
| RAG 无结果 | 重新措辞/通道尝试，保持适用条件；仍不足则证据不足 | 把零召回等同「没有限制」 |
| 数据新版本发布 | 旧 run 可继续用未撤销的不可变旧 release；结果注明版本 | 混读新计划、旧规则和旧向量索引 |
| release 被撤销 | 恢复/发布失败，提示新建修订 run；旧结果标已过时 | 静默在旧 run 换数据却保留旧确认 |
| 人工等待到期 | run → EXPIRED，后续同 session 新 run | 原地复活终态、把 7 天保留当 7 天有效 |
| 预算耗尽 | 停止新模型调用；仅可用已验证结果/同门禁模板，否则失败 | 降级跳过资格或事实校验 |
| 用户取消 | CancelRun 原子记取消；worker 停后续工作转 CANCELLED | 保证已发出厂商调用一定撤回/免计费 |

> 重试上限：模型每个逻辑调用最多 **2 次**供应商尝试（SDK 内部自动重试计入同一上限）；algo 瞬时只读故障最多 **2 次**总尝试；所有尝试受统一剩余截止时间约束。格式错误导致的语义修正用**新逻辑调用**并计入节点修订上限，不藏在网络重试里。

**用户修改方案（REVISE_PLAN）**：针对指定 `result_version` 提「更保守 / 不要某城市 / 成绩改了」→ gateway 鉴权后提交 REVISE_PLAN → orchestrator 在**同 session 创建新 run**、记父结果版本、原结果不变 → 提取为画像 patch、区分软偏好/硬要求、生成新 `profile_version`（原结果非新版本默认授权）→ **首版统一使全部下游失效**，重新确认后按步骤 7–15 执行（成绩/选科/报考范围变化尤其不得只重排旧池）→ 新结果列出画像变化、版本变化与方案差异。（未来只改软偏好可复用同 release 候选池，但须先实现依赖追踪 + 回归测试。）

**政策问答（POLICY_QA）**：只补齐问题所需的学校/报考年/省份·适用范围，**与问题无关的成绩、健康信息不采集** → 按发布版本调 RAG，涉及精确招生人数/分数时用领域查询能力（无对应接口就明确补契约，**不假称四 RPC 已涵盖任意资料查询**）→ 生成带原文证据的答案并验证，无可靠资料答「当前证据不足」+ 给已核验来源线索 → **只输出政策解释，不自动推导「你有资格报考」**（要个性化资格判断则切换生成/资格流程并补信息）。

**方案解释（EXPLAIN_RESULT）**：读取用户有权访问的指定 `result_version`、当时画像/数据版本与验证记录 → 说明为何这样排序、概率怎么估、有哪些限制/保底告警，**不偷偷改候选、权重或顺序** → 解释也走事实校验；若引用版本已撤销先提示结果过时，重新评估需创建 REVISE_PLAN。

## 9. 里程碑与发布计划

阶段顺序为 A→F（源自审查报告 §10.1，已吸收为本 PRD 权威顺序）：**先用现有算法形成受控最小闭环，再加智能增强**。算法四 RPC 已实现，故算法闭环前置，不再排在多 Agent 之后。

| 阶段 | 交付物（产品视角） | 验证目标（退出条件） |
| --- | --- | --- |
| M1 · 规格对齐（A） | 主链 / 能力标签 / 画像·任务·事件 schema / 发布门禁定型 | 流程每步映射到已有接口或明确新增契约 |
| M2 · 可靠任务底座（B） | 持久受理 + worker + 真实 interrupt/checkpointer + 恢复幂等 + SSE/GET/取消 | 用测试替身即可通过断网 / 崩溃 / 并发恢复测试，不需真实付费模型 |
| M3 · 算法最小闭环（C） | 接入现有四 RPC + 确认画像 + 结构化结果 + 模板校验（受控 ALGORITHM_PREVIEW） | 数值可复现、可审计，与 LLM 边界清晰；不得宣称全部资格已核验 |
| M4 · 生产资格与证据（D） | 数据入库 / ETL 四层质检 + 双路检索 + 当年规则链 + release 版本读取 + 三类证据 + 隐私删除 | 检索 recall@k 达标、分流正确；未知资格 / 错版本 / 错引用不能通过发布门禁 |
| M5 · 模型治理与表达（E） | llm-gateway 预占 / 结算 + 受控画像解析与报告生成 + 失败模板 + CI 评测门禁 | 并行 / 超时 / 供应商失败下预算可核对，报告不改写数值与资格，回归不通过即阻断 |
| M6 · 智能增强（F，P1） | Strategy / Critic / 政策问答 / 解释·修订子图 + 全链路观测 + 压测；第二场景复用为可选 | 在已有门禁之上有可测收益，循环有限且不降低可靠性；P99 / 成本有真实数据 |

里程碑对应三个发布层级：

- `ALGORITHM_PREVIEW`：M3 退出后仅作内部受控验证，不作为正式志愿方案；
- `V1_DEMO`：完成 M5 的全部 P0、验收场景与安全门禁后可公网演示，结果仍须标注为历史参考，P1 增强可延后；
- `V1_FORMAL`：完成全部 P0 + P1，并关闭所有 `REVIEW-P1-*` 阻塞问题后才可称为正式推荐发布。

完成单个里程碑不代表可上线；任何层级都不得绕过资格、版本、事实校验与失败即关闭门禁。

部署阶梯：L0 本地直跑 → L1 docker-compose 一键起全栈 → L2 单台 VPS 公网演示（Caddy + HTTPS + SSE 不缓冲 + 数据子集 + 限流）→ L3 k8s（可选）。**V1 目标：L1 + L2 最小演示。**

## 12. 验收总则

1. 功能需求逐条按「验收标准」实测，区分**设计目标**与**已实现能力**，不以文档描述代替实测；
2. `V1_DEMO` 要求 P0 全部通过、G1–G6 达到已定义阈值、四层测试与安全门禁通过；`V1_FORMAL` 还要求全部 P1 与 `REVIEW-P1-*` 阻塞问题关闭；
3. 任何「无可靠数据」场景必须明确告知用户，验收时以「不假装成功」为通过条件；
4. **本 PRD（v1.3）已吸收 `agent-architecture-review.md` 的全部目标态结论，是目标态唯一权威**；review.md 降级为历史存档、不再单独维护。若发现 PRD 与 review 存档不一致，**以 PRD 为准**，并在 review 存档顶部标注该处已被 PRD 取代；
5. **冲突裁决分工**：目标态（要做成什么样）以本 PRD 为准；代码现状（做到哪了）以 `gap-analysis.md` 实测为准；决策理由（为何这么定）以 `docs/adr/` 为准。每条 P0 需求须标注「设计目标 / 已实现」，未标注者默认视为设计目标，不得作为已具备能力对外声称。

## 13. 关键验收场景（20 条 · 端到端门禁）

> 吸收自审查报告 §10.2。每条既是验收用例，也是 §5.2 主链路各门禁的可测化。测试分层：纯状态/规则单测、跨服务契约测试、受控故障注入、真实数据回归、上线前隐私/安全检查——**不必每次单测都调用付费模型**（M2 起用测试替身，见 ADR-0003）。

| 编号 | 测试输入 / 故障 | 必须观察到的结果 |
| --- | --- | --- |
| T01 | 合法且规则资料完备的省年科批画像 | 候选/概率来自 algo；完整确认、验证、发布及 GET/SSE 一致 |
| T02 | 缺成绩/省份，连续 6 次未补齐 | 不进入算法；返回关键字段不足，无伪完成结果 |
| T03 | 只给位次，现有接口未扩展 | 明确能力边界，**不反向编造分数** |
| T04 | 同一确认双击、两标签页不同回答 | 相同命令一次生效；冲突回答被拒；下一次合法中断可继续 |
| T05 | 中断持久化前后、回答提交后分别崩溃 | 不出现「已通知但无检查点」或重复应用回答 |
| T06 | worker 在模型请求后崩溃、另实例接管 | 旧 epoch 不能发布；账本保留未知计费，不无限重试 |
| T07 | 用户在计算/发布中断网或重启 gateway | run 独立完成；订阅补发或 GET 得到同一结果 |
| T08 | 多个模型调用同时接近预算上限 | 原子预占限制总额；账本可区分语义调用与供应商尝试 |
| T09 | 600 分确认后改成 580 分 | 新 `profile_version`；旧位次/候选/证据/报告均失效 |
| T10 | 执行中发布新数据或撤销旧 release | 普通更新不混读；撤销阻断恢复和发布，并提示重新生成 |
| T11 | 章程零召回、规则缺失、体检未知 | 分别标明原因；**不能推断无限制或资格通过** |
| T12 | 组内部分专业受限、组成员跨年变化 | 不声称全组专业可报；标记历史可比性与当年资格范围 |
| T13 | 报告数字被改、引用错学校/年份 | 数值/适用性校验阻断；达到重写上限仍不能发布 |
| T14 | 保底不足但资格和事实通过 | 正常结构化结果带醒目风险告警，**不伪报 `safe_guard_ok=true`** |
| T15 | 取消与最终发布同时发生 | 仅一个合法终态；已发送厂商调用费用仍可结算 |
| T16 | 非所有者查询/订阅/恢复/取消 | 全部拒绝，不能靠猜 `run_id` 读出画像 |
| T17 | 政策问答、解释已有结果、修改偏好 | 各走对应子图；问答不收无关成绩，解释不悄悄重算 |
| T18 | 用户删除数据、日志/缓存检查、备份恢复演练 | 敏感数据不进入不必要系统，删除策略贯穿派生数据 |
| T19 | 全量候选很大、模型上下文被限制 | 权威全集仍保存，优化不因 prompt 截断失去保底候选 |
| T20 | 模型调用不可用或预算不足 | 仅返回经同门禁的模板/既有结果，否则明确失败 |

> 观测口径：同时统计主动执行时间、人工等待、排队、节点重试、预算预占/结算、未知资格与门禁拒绝率。里程碑退出条件见 §9；实施顺序（A→F）见 §9 与 gap-analysis §5。
