AI 高考志愿智能决策系统 · 实现现状与设计分析

多 Agent 编排 + RAG + 确定性领域算法，解决考生「不知道该问什么」的模糊决策需求。

仅覆盖湖南省新高考 3+1+2 模式，其他省份不在范围内。

1. 项目定位与范围

本项目是一个高考志愿填报的智能决策 Agent 系统：用户以自然语言（或结构化输入）描述成绩与偏好，系统通过多轮对话采集画像、经用户确认（HITL）后，由确定性算法生成「冲 / 稳 / 保」分档的院校专业组候选池，估计录取概率，做硬约束校验与志愿表优化，最终产出带证据、风险提示与免责声明的志愿方案报告。

  • 产品原则：LLM 管语义 / 生成，确定性代码管数值 / 规则 —— 「LLM 不许算数，算法不许编话」。
  • 数据边界：湖南省新高考 3+1+2；历史数据 2022–2024 作训练窗口、2025 作验证；5700+ 院校招生章程原始文档。
  • 安全底线：禁止任何「保证录取」表述；无可靠数据时明确输出「不予推荐 / UNKNOWN」，宁报错不编数据。

2.2 核心设计原则（工程红线）

红线含义
LLM 不许算数位次 / 概率 / 规则 / 配比一律由 svc-algo 给出；LLM 只写解释文案，不得生成或改写数值与候选身份。
强结构化数据只走 SQLpgx + sqlc 参数化查询；RAG 仅用于非结构化章程文本，检索内容视为数据、显式分隔转义。
图控制权归 orchestrator下一步 / 条件补问 / Critic 回边由 orchestrator 裁决；gateway 只转交命令与事件。
可复现纪律（svc-algo）单线程、全序排序带 tie-break、禁 map 迭代产序；同输入同输出。
宁报错不编数据无可靠数据 / 无规则覆盖时明确告知「不予推荐 / UNKNOWN」，不得伪造概率。
禁止「保证录取」报告必带风险提示与免责声明；算法预览明确标注非录取保证。
密钥不入 Git只放 .env / secrets；模型 key 仅存在于 llmgw 侧。

4. svc-algo 算法服务（唯一成体系的已实现能力）

4.1 Kratos 三层结构

层包职责与约束

(algo.go / dto.go / error.go)		薄层：每个 RPC 只做 ①解析校验入参 ②调一个 usecase 方法 ③biz↔pb DTO 映射 + toKratosErr 错误映射。dto.go 保证 fromPb(toPb(x))==x round-trip 一致（slice/map 空→nil 约定）。

4.2 四个 RPC 的算法设计（一 RPC = 一 usecase）

RPCusecase算法要点
RankConvert RankUsecase.Convert 分数→位次正向换算（基于一分一段表 score_rank_map，按批次互斥分数分区，含 control_score 控制线列）。仅正向，不做 rank-only 反推（符合 R7 口径）。
EstimateProb RecommendUsecase.EstimateProb 编排链：rank.Convert → LoadCandidates（院校专业组为候选单位，GroupKey 内存合并）→ CheckConstraints 选科过滤 → BatchGroupHistory/Plan → RecommendCandidates。概率用加权命中率法，钳制 [0.01, 0.99]；基准年窗口 = [year−W, year−1]，不含报考年（防验证泄漏）；末尾回填 AuditBasis（sampleYears / UserRank / UserPercentile，与 RankConvert 同源口径）。候选按概率分档：冲 / 稳 / 保。
CheckConstraints RecommendUsecase.CheckConstraints 纯函数无 Repo。subject_req 文本解析：全角逗号切首选/再选；再选「不限」→none、单科→all、「X/Y(2选1)」→atLeastOne、「X、Y(2科必选)」→all；政治→思想政治归一；组级 match-any；按输入序保序。目前仅实现选科维度——单科/体检/性别/学费需等规则发布链路（M4）。
OptimizeWishlist OptimizeUsecase.OptimizeWishlist 五步：按 Category 分组 → 按风险偏好配比（RiskAppetite 覆盖 TargetRatio）定向配额 round(L×ratio)、保档兜底 L−rush−stable、不足空位按全局 utility 降序补 → 全序排序赋 FinalRank → checkSafeGuard 保底校验。效用打分四维：tierScore / majorScore（子串匹配）/ locationScore（城市 1.0 / 同省湖南 0.8 / 其他 0.5）/ strengthScore（0.4 硕士点 + 0.3 博士点 + 0.3 软科），min-max 归一 + 偏好维度加权（PriorityDims×2，归一 Σ=1）。滑档率用解析式 Π(1−pᵢ) 取代蒙特卡洛；SafeGuardOK=false 是告警非 error。

4.3 可复现纪律（确定性保障）

三条硬纪律贯穿全部算法代码：①单线程执行不引入并发乱序；②全序排序带 tie-break（如 lessByUtilityThenKey：Score↓ → UniversityCode↑ → MajorGroup↑），杜绝排序不稳定；③禁止 map 迭代产序，遍历走固定维度 slice。同输入必同输出，这是「算法结果可审计、可回放」的基础。

5. svc-orchestrator 编排服务（Python / LangGraph）

5.1 RunLifecycle：持久 run 生命周期（核心底座，约 2700 行）

app/run_lifecycle/service.py 是整个编排服务的唯一公开 seam，实现了 PRD §5.2 中步骤 1–7 + 15 的受控子集：

QUEUED→ worker 领取(租约) → RUNNING→ interrupt → WAITING_HITL→ ResumeRun → QUEUED / RUNNING→ SUCCEEDED / FAILED / CANCELLED / EXPIRED
  • 命令接口：SubmitRun（幂等受理，同幂等键重放原回执）、ResumeRun（回答/确认指定 interrupt，校验所有权、状态版本、profile_version、interrupt 未过期未消费）、GetRun、CancelRun（处理取消与发布竞态）、WatchRun（持久 event_seq、typed progress/interrupt/result/error 事件、游标补发与断线重订）。
  • 并发安全：worker 租约 + lease_epoch fencing（防旧 worker 写入），执行/HITL 双时限，到期 HITL 自动过期；有检查点 ≠ 有执行权，执行权由租约裁决（收口审查问题 P1-09）。
  • 断点续跑：官方 langgraph-checkpoint-postgres 承载检查点（ADR-0002）；receipt / interrupt 原子恢复。
  • 画像模型：不可变画像 revision（profile_revision），确认绑定 profile_version，修正生成新版本（profile.py 约 370 行）。
  • release 绑定：run 创建时绑定内容哈希不可变 release_id（ADR-0004），algo 查询按 release 过滤，防止跨版本数据漂移。

5.2 LangGraph 画像图（interrupt / resume 双闸门）

profile_graph.py 定义了当前真正运行的业务图，结构刻意精简：

prepare_profile→ pause_for_user
interrupt：画像确认卡→ CONFIRM_PROFILE → wait_for_execution
内部执行闸门 interrupt→ worker 恢复 → algorithm_preview→ END

两个 interrupt 的分工：用户闸门（画像确认，等待人类回答）与内部执行闸门（确认写回业务库后由 worker 恢复，保证执行权与租约一致）。拒绝/修改画像则走 END 或生成新 revision 重新确认。

另有旧图骨架 graph/build.py（intake → profile_confirm → retrieve → check_conditional），护栏常量已就位（补问上限 6 / Verifier 重试 2 / Critic 回边 2，与 PRD v1.3 对齐），但四个业务节点仍是 TODO 桩，属 M2/M6 后续接线对象。确定性完整性闸门 state.py::check_completeness 是纯函数（符合「LLM 不当闸门」原则）。

5.3 算法预览流水线（受控 ALGORITHM_PREVIEW）

用户确认画像后，RunLifecycle 通过 GrpcAlgoClient（algo.py，grpc.aio）串联 algo 四 RPC，并在发布前执行多重确定性门禁（对应审查问题 P1-14 的收口方式）：

  1. RankConvert：run 绑定 release_id 传入，校验 reply rank 与后续 EstimateProb 的 AuditBasis 一致（同源口径校验）；
  2. EstimateProb：传确认后省/年/科/批/分数/选科，校验概率范围 [0.01,0.99]、候选身份、重复/漂移、执行时限；
  3. CheckConstraints：只把 kept 候选送入下一步；
  4. OptimizeWishlist：结果连同候选、概率、AuditBasis 原样发布为 ALGORITHM_PREVIEW（编排层不改写任何数值与候选身份）；
  5. 预览非空才发布，且明确标注非录取保证；正式推荐发布仍需 M4/M5 的规则/证据/报告门禁。

6. svc-gateway 网关（Go / Kratos）

internal/gateway/service.go（448 行）定位是纯接入层——「只做接入与门控；run 生命周期和图内控制归 svc-orchestrator」，内部不含第二套状态机（仅依赖 runClient 最小传输接口）：

  • 命令转交：CreatePlan → SubmitRun；ConfirmProfile / BackfillProfile → ResumeRun（按 answer.type 分派 CONFIRM_PROFILE / REJECT_OR_EDIT_PROFILE / ANSWER_FIELDS / DECLINE_FIELDS 四类回答）；GetRun / CancelRun / WatchRun 直接透传。
  • 鉴权：x-principal-id 必填（gRPC metadata 或 HTTP header），缺失返回 PRINCIPAL_REQUIRED；入站校验后以 outgoing metadata 传给 orchestrator。
  • 幂等：IdempotencyKey 必填校验；回执状态映射 accepted / replayed / rejected。
  • SSE 事件流：RegisterRunEventStream 挂 GET /v1/runs/{run_id}/events，typed RunEvent 以 protojson 写入标准 SSE（id=event_seq, event=type），15s 心跳不占业务序号，支持 Last-Event-ID 头与 after_event_seq 查询参数断线重连——SSE 连接不承担任务生命周期（收口 P1-08）。
  • 未实现：令牌桶限流 + 并发闸门（FR-21，M2/M4）。

7. svc-llm-gateway（未实现，设计已定）

当前 internal/llmgw/service.go 仅 38 行：Chat / StreamChat 均返回 TODO。目标态设计（FR-20 + ADR-0003）已明确：

10. RAG 检索与数据资产

  • HybridRetriever（rag/retrieve.py）：双路召回 —— pgvector 向量语义路 + pg_trgm 关键词路（ILIKE / similarity），RRF（k=60）融合，确定性 tie-break，SQL 全参数化；meta 硬过滤目前仅 school_name / year（province / category 待补）。
  • ETL 管线（rag/etl.py 376 行 + scripts/ingest_charters.py）：从 docs/charters/2025/ 的 5700+ 院校章程 txt/json 原料摄取入库；scripts/qa_check.py 质检（四层质检防线的完整核实属 M4）。
