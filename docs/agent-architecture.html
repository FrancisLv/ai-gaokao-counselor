1设计目标与约束

G1 · 幻觉零容忍每条结论必须可溯源到原文；验证器逐条比对，不合格打回重写。
G2 · 规则硬约束选科/单科/体检/批次等为硬规则，由确定性代码裁决，不交给 LLM。
G3 · 数值可解释位次换算与录取概率必须给出计算依据，可复现、可审计。
G4 · 时效性招生政策逐年变化，知识必须走检索而非模型参数。
G5 · 成本与延迟可控按角色路由模型，缓存 + 限额 + 熔断，P99 与单次成本可观测。
G6 · 可评测golden set 进 CI，回归不通过即阻断发布。
明确非目标（写进文档，约束范围）
  • 不做通用聊天助手；不做多学科家教；不做院校排名预测
  • 不做志愿「代填」，系统只提供决策支持，最终由用户确认
  • 不采集任何未成年人个人敏感信息，不做用户画像商业化
核心架构原则：LLM 负责语义理解、规划与表达；确定性代码负责规则、数值与约束。两者边界必须清晰。

2AI 适用性分析：哪里该用 AI，哪里不该

这一节回答一个必须回答的问题
「这不是传统志愿填报工具就能做吗？为什么要用 AI？」
这是本项目在面试中 100% 会被问到的问题。答不好，整个项目会被判定为 「为了用 AI 而用 AI」。本节给出经得起追问的答案，它也是第 7、8 章架构决策的论证依据。

2.1 先承认对方是对的

诚实地说：在「精确匹配与数值计算」上，传统做法确实更好，AI 更差。

能力传统做法（志愿填报工具）AI
精确数值查询强：SQL 查库，零误差弱：会算错、会幻觉
规则过滤强：布尔判断，确定弱：不稳定，会漏
结果一致性强：同输入同输出弱：有随机性
成本低：查询几乎免费高：每次调用付费
延迟快：毫秒级慢：秒级
结论一
如果需求只是「输入分数 → 输出符合条件的院校列表」，那不需要 AI。 这类工具已经做得很好，而且在精确性上做得比 AI 好。
面试时先讲这一层。它证明你懂边界，而不是被 AI 热潮冲昏头。

2.2 AI 真正加了什么（五项，每项都对应「传统做不到」）

#AI 的价值传统做法为什么做不到
1 把「人话」变成「查询条件」
用户说：「我儿子物理类 580 分，想学计算机，家离江苏近点，预算别太高，他不太喜欢纯理论的。」		 传统系统要用户填十来个字段、点几百个筛选器。「不太喜欢纯理论的」不是一个字段，直接卡住
2 模糊偏好的语义映射
「别太理论」→ 计算机类下偏应用 / 偏理论的分野
「离家近」→ 结合所在地做地理推断
「好就业」→ 把「就业」映射到专业与行业		 这些是语义问题，不是字段匹配。传统工具只能让用户自己在预设标签里选，而多数考生和家长根本不知道有哪些标签可选
3 非结构化知识的问答
「这个学校转专业政策是什么」「大类招生怎么分流」「保研率多少」		 答案在招生章程、政策文件里，是文本不是字段。传统系统只有结构化字段，答不了。这正是 RAG 的位置
4 生成式解释，而不是给个表格
为什么这个在「冲」、那个在「稳」，和哪个偏好契合、哪里冲突、风险是什么		 传统只能给列表或套模板；模板覆盖不了个性化权衡
5 多轮追问与修正
「不想去东北」「再加两个保底的」「这个专业具体学什么」		 传统是「一次性查询」，不支持协商式探索

2.3 产品层面的真正差异

传统工具的核心假设是：用户已经知道自己要什么，只要给他好用的筛选器就行。

现实是：一个 17 岁的学生和家长，面对 3000 所院校、800 个专业， 最大的痛点不是「筛不出来」，而是「不知道该问什么」。 他们本身是模糊的，需要被引导、被解释、被追问。

传统工具解决：明确的用户 → 高效检索
本项目解决：模糊的用户 → 逐步明确 → 可解释的方案

AI 的价值不在「让筛选更准」，而在「让模糊的人也能得到答案」。 这是产品定位的差异，不是技术炫技。

2.4 判断一个场景该不该用 AI：三条标准

标准本项目
① 输入是否非结构化 / 模糊？是：自然语言 + 模糊偏好  ✓
② 输出是否要求生成 / 解释？是：方案 + 理由 + 风险提示  ✓
③ 是否有大量非结构化知识需检索？是：政策、招生章程、体检规定  ✓

三条全中 → 该用 AI。反过来说：若需求只是「分数 → 院校列表」，那确实不该用。

这个框架可以直接在面试里讲
它展示的是方法论，而不是「我觉得 AI 好」。 知道什么时候不用 AI，比知道什么时候用 AI 更能说明水平。

2.6 面试答法：三层结构 + 一个杀手锏

第一层 · 承认边界
「核心的匹配和数值计算，传统做法确实更好。我保留了它们——结构化数据走 SQL 精确查询，规则用确定性规则引擎，位次和概率用算法。这些环节我故意不用 LLM。」
第二层 · 划清 AI 的职责
「AI 只负责三件传统做不到的事：把模糊的自然语言转成结构化查询意图、 检索非结构化政策文本、生成可解释的方案。这三条是表单式工具的结构性盲区， 不是优化能解决的。」
第三层 · 用数据收尾（杀手锏）
「我做了对比测试：面对模糊输入（如「想学计算机但别太理论」）， 纯筛选器方案的可用率是 X%，加入自然语言理解后是 Y%。 差别不是「更准」，是「原来根本没法用」。」
（X / Y 由第 11 章的评测体系产出，务必填真实数字）

第三层是决定性的：大多数人只能「说理由」，而你能「给数字」—— 这说明你不是觉得，是测过。

为什么这样分层
  • 编排用 LangGraph，Go 守住治理与算法：图与状态交给行业标准框架（拿岗位入场券、省下 4–8 周引擎工时），Go 专注框架之上的成本治理、HITL 门控与领域算法——差异化来自框架做不到的部分，而不是重写框架。
  • Python 收敛在推理/检索/评测：只做它生态最强的事，接口用 gRPC 隔离，未来换模型/换向量库不影响 Go 侧。

4.1 心智模型：两类程序 + 一个数据仓库

先把整个系统压缩成一句话：它只有两类程序，外加一个它们共用的数据仓库。

Go · gateway / llm-gateway / algo控制平面：门口的保安 + 会计。入口请求进 gateway；模型治理在 llm-gateway；算数、裁规则在 algo（三者可同一份代码、按角色部署）。
Python · svc-orchestrator智能平面：专家团。理解人话、查资料、写方案、自我审查——所有需要 LLM 与 RAG 的活都在这里。
数据仓库档案室：PostgreSQL(+pgvector/tsvector) · Redis · 对象存储。两种语言都读写它。
一句话边界
Go 管「控制与治理」，Python 管「智能与检索」，数据层两者共用。
规则判定与数值计算绝不交给 Python 的 LLM 去算；语义理解与生成绝不在 Go 里硬编码。 （论证见第 7 章的核心决策、第 8 章的算法层。）

关于「文档里那个 Orchestrator 服务」
第 12 章把编排画成一个独立的 Orchestrator 服务；这里把编排并进 svc-orchestrator。 原因：LangGraph 运行在 Python 进程内，起步阶段没必要为它单起一个服务（要不要独立见 4.7 决策点）。 通用惯例是：先合并，等有了真实的拆分理由（扩缩容差异 / 故障隔离 / 团队边界）再拆。
为什么 Go 要拆成多个角色（本方案的关键）
如果一个 Go 进程既做客户端入口（在 Python 上游）、又做 LLM 网关（在 Python 下游），就会形成双向同步调用 → 环路，有循环等待 / 池耗尽死锁的风险（详见 4.9）。
拆成 svc-gateway / svc-llm-gateway / svc-algo 三个角色（可同一份代码、按角色部署，但必须不同地址 / 不同部署）后，调用链变成单向的 DAG：gateway → orchestrator → { llm-gateway, algo }，不再成环。

为什么这样就不成环
上游（svc-gateway）、中游（svc-orchestrator）、下游（svc-llm-gateway / svc-algo）各一层，箭头只向下。
· svc-gateway 只调 svc-orchestrator，不碰下游；
· svc-orchestrator 只调两个下游（svc-llm-gateway / svc-algo），不回调 svc-gateway；
· 两个下游只调模型 / 数据库，都不回调 svc-orchestrator（所以云模型由 svc-llm-gateway 直连，而不再转发给 Python）。

本地模型例外
Embedding / Rerank 走本地小模型（无 key、无成本），由 svc-orchestrator 内部完成，不经过 svc-llm-gateway——既省一跳，也不破坏 DAG。只有「需要计费 / 路由 / 治理的云端 LLM」才经 svc-llm-gateway。

分数线、招生计划这类强结构化数据 → 直接进 SQL，不进向量库； 政策、章程、体检规定这类非结构化文本 → 才走 RAG（切分 + 向量 + 倒排）。
这是第 7 章的核心决策：数值错一个字就是事故，不能靠「检索」去碰运气。

4.5 一次「生成志愿方案」的数据流（在线）

下面用数据视角重走一遍主链路（步骤细节见第 5 章）。注意每一步数据「变成了什么」。

#在哪发生数据进来数据出去（变成什么）
1svc-gateway用户自然语言会话 + trace_id，写 PG
2Python · INTAKE自然语言结构化画像 JSON；查缺 → 追问(interrupt) → resume 循环，闸门校验必需字段
3HITL（svc-gateway 推送）画像卡片用户确认 / 修正 → ResumeGraph

这就是为什么不能只用 LLM：每一次「变身」里，数值 / 规则 / 排序都必须由确定性代码接管。

4.6 状态存在哪：为什么各服务都「无状态」

  • LangGraph 每推进一步，就把状态快照写进 PostgreSQL（plan_checkpoint 表）。断点续跑、HITL 恢复、时间旅行重放，全靠它。
  • 因此 Python 进程可以随便重启——「记忆」不在内存，在 PG。
  • svc-gateway / svc-llm-gateway / svc-algo 同样只读写 PG 与 Redis，不存本地状态 → 四个服务都能水平扩容。
  • llm_call_log 表：每次 LLM 调用的 token / 成本 / 延迟 → 成本曲线与预算闸门的数据来源。
这条设计是面试加分点
「把运行态外置到数据库、让应用进程无状态」是生产系统的标准动作， 也是你能拿真实压测数据（QPS / P99 / 滚动发布）说话的前提（见第 12 章）。

4.7 决策点：LLM 调用要不要「绕经」Go 网关

这是文档里唯一没说死、需要你拍板的地方
第 3 章把「LLM Gateway（Go）」列为能力层，第 10 章的契约又写「role 由 Go 指定，模型路由与成本控制留在 Go」； 可 LangGraph 节点跑在 Python 进程里，节点要调 LLM 时天然是 Python 发起——于是产生两条路。
方案调用路径优点代价
A（严格） Python 节点 → gRPC → Go LLM Gateway → 模型 Go 全程掌控 role→模型 路由、缓存、预算、记账，最贴合文档叙事 多一跳；若不做角色拆分，会形成双向调用、有死锁风险（见 4.9）
B（简单） Python 节点 → 模型 API（直连） 起步最快，少一跳，调试简单 路由逻辑分散两边，Go 不完全在调用路径上，只能靠「下发配置 + 读日志表」间接治理
建议（与 4.9 的关系）
代码结构按方案 A 预留（三个角色目录已就位），但运行时调用在 M1–M2 先走方案 B（Python 直连模型，省一跳、快速验证）。 到 M5 工程化阶段，把运行时也收口成 A——让 svc-llm-gateway 真正挡在调用路径上，实现前置成本闸门。
4.9 的 DAG 拆分是终态架构；本节说的是起步阶段的务实妥协。两者不矛盾，只是时间线不同。
⚠️ 选 A 必须先解决一个副作用（见 4.9）
方案 A 天然引入双向调用：Go 既在 Python 上游（入口）、又在下游（LLM 网关）→ 形成环路，有死锁风险。
本方案的做法是把 Go 拆成 svc-gateway / svc-llm-gateway / svc-algo 三个角色，让调用链单向、无环。详见 4.9 调用拓扑与环路消除。

4.8 为什么用两种语言（Go + Python）：论证与面试答法

这一节回答的问题
「为什么用两种语言？只用 Python 不行吗？」——这是面试里 100% 会被问到、也是唯一可能被质疑「过度设计」的地方。下面给出论证骨架与可直接背的话术。

先分清两个问题

  • 对系统本身：早期纯 Python 更省事，混合更能上规模——两者都成立。
  • 对你个人（7 年 Go）：纯 Python = 自废武功；混合 = 把唯一的稀缺资产变成护城河。

纯 Python vs 混合

维度纯 Python混合（Go + Python）
开发速度快，单人首选慢一档（要维护 proto / gRPC / 两套 CI）
调试单语言，简单跨语言两跳，麻烦
高并发网关 / 限流弱（GIL，不如 Go 稳）强（Go 主场）
成本 / 配额 / 可观测能写，但不专业强（Go 治理层）
差异化叙事弱：同质化强：「我能把 Agent 做成生产级后端」
生态契合度最高（全原生）略低（需接口隔离）
单人维护成本低高
但混合最大的坑
它很容易变成过度设计：一上来就 proto + gRPC + 双向调用，会花好几周在脚手架上，而不是在决定系统靠不靠谱的检索质量与评测上。 所以「混合更好」有个前提：纪律——按 M1–M6 分阶段注入 Go，Go 只放「框架做不到 + 你有优势」的地方（见第 15 章）。

答法一 · 30 秒版（先背这个）

「因为系统里有两类本质不同的活。智能那部分——编排、RAG、推理、评测——我从一开始就放在 Python 的 LangGraph 里，那是这类项目的行业标准，生态也最强。控制与治理那部分——网关、并发、限流、成本闸门、可观测，还有位次 / 概率这类领域算法——是长期运行的生产后端，我用 Go。
一句话：Python 把智能做出来，Go 把它做成能上生产的服务。」

答法二 · 2 分钟三层结构

第一层 · 先承认边界（先泄压）
「如果这个项目只是做个 RAG demo 或聊天机器人，我会用纯 Python，而且那样更好、更省事。我不会为了显得高级硬上两种语言。」
第二层 · 划清两类工作，为什么必须分开
智能侧（Python 唯一合理）：LangGraph 编排 + 状态 / 检查点 / 断点恢复 / 人工介入；RAG（向量 + 倒排 + RRF + rerank）；推理、评测 → 生态牢牢在 Python。
控制侧（Go 明显更强）：API 网关 + 流式 + 高并发扇出；限流 / 配额 / 熔断降级；LLM 成本「前置」闸门；跨语言可观测；领域算法（位次换算 / 概率估计 / 规则引擎 / 志愿表优化 / 投档模拟）。
「这两类塞进一个 Python 运行时，控制侧会被拖累，智能侧又用不上 Go 的好处。」
第三层 · 一句话边界 + 直接回答「为什么纯 Python 不行」
「Python 负责智能，Go 负责治理。纯 Python 不是做不出来，而是在三件事上吃亏： ① 网关 / 治理的并发与稳定性； ② 成本、配额、降级这类生产级治理，不是 Python 的强项； ③ 也是最现实的——纯 Python 我会和一大堆只会 Python + LangChain 的候选人撞在一起，没有区分度。」

杀手锏 · 用数字收尾

「为了证明不是拍脑袋，我做了对比：把 LLM 成本闸门前置到 Go 网关后，多轮循环下的单会话成本下降了 X%；或者同一压测下，Go 网关 P99 是 A ms，Python asyncio 网关是 B ms。差别不是『更快』，是『能不能稳定扛住』。」
⚠️ X / A / B 必须是你真跑出来的数字。没测就先别讲——空话会反噬。

主动堵住四个追问

追问答法
为什么不干脆全用 Go，把 LangGraph 也重写？编排引擎是别人已做到极致的东西，自研要 4–8 周纯投入，还会丢掉 LangGraph 这张岗位入场券（见第 15 章）。差异化不该来自「谁跑这张图」，而该来自框架之上的治理与领域算法。
为什么不全都用 Python？AI 生态确实是 Python 的决定性优势，所以智能侧我全用 Python，没有重造。但治理与算法不是 AI 生态问题，是后端工程问题，那里 Go 更合适。
两种语言维护成本不高吗？边界我刻意收窄成一条：只用一个 .proto 做单一契约，gRPC 隔离，两边都无状态、运行态都在 PG。这不是随意拼，是刻意的架构边界——两边能独立部署、独立测试。
你是不是因为只会 Go 才用 Go？坦白 + 反打：「我 7 年确实主要是 Go 工程师。但我没有为了用 Go 而用 Go——最核心的编排我故意留在 Python。这套边界换一个只会 Python 的团队一样成立，只是两边比例会变。」
如果对方就是不认同「要两种语言」
别硬刚，顺势转：「我完全能用纯 Python 单独交付这个系统；Go 那部分是我额外带来的工程能力。如果团队是纯 Python 栈，我不会坚持，但成本治理和领域算法这块的思考照样带得进来。」—— 把「分歧」变成「我多一层能力」。
总提醒
全程别出现「我觉得 Go 更好」这种偏好式表达。你要传递的是：「这是一种职责切分，而且我想过什么时候不该这么切。」知道什么时候不用两种语言，比坚持用两种语言更能说明水平。

4.9 调用拓扑：为什么会成环、如何消除（DAG 化）

问题：Go 同时在上游和下游
如果 Go 既做客户端入口（在 Python 上游）、又做 LLM 网关（在 Python 下游），两端会同步地互相调用： 
Go 网关 ── 调用 ──► Python 图 ── 回调 ──► Go 的 LLM 网关 ──► 模型
   ▲                                                          │
   └────────────────── 同一个 Go 服务 ◄────────────────────────┘

会带来什么

问题说明
循环等待 / 池耗尽Go 等 Python，Python 等 Go；若两者共用受限的 worker / 连接池 → 谁都等不到对方，低负载没事、上量就炸。
循环依赖Go 依赖 Python，Python 又依赖 Go → 启动顺序、版本对齐、回滚都变复杂。
延迟叠加一次 LLM 调用变成往返折返，每一跳都在关键路径上。
故障环两边的失败域耦合，谁挂都连累对方。
根因
按「语言」切角色，而不是按调用方向切 → 同一个 Go 同时站在 Python 的上游和下游 → 必然成环。

本方案的解法：拆角色，做成 DAG

把 Go 拆成三个部署角色（可同一份代码）：

角色位置职责
svc-gatewayPython 的上游客户端入口：HTTP/SSE、鉴权、限流、会话、HITL 门控
svc-llm-gatewayPython 的下游LLM 网关、成本 / 预算（持有 key）
svc-algoPython 的下游领域算法

调用链变成单向链：客户端 → svc-gateway → svc-orchestrator → { svc-llm-gateway, svc-algo } → 模型 / DB，环消失（见 4.3 的调用图）。

关键约束
两个下游（svc-llm-gateway / svc-algo）都不能回调 svc-orchestrator。因此云端 LLM 由 svc-llm-gateway 直连模型 API（而不是「再转发给 Python 去执行」）。 本地模型（Embedding / Rerank）反过来留在 svc-orchestrator 内部、不经过 svc-llm-gateway——这样下游都不回调上游，DAG 才成立。

三种解法对照（本方案选 A）

解法做法结果
A（已采用）拆 Go 为 gateway / llm-gateway / algo 三角色 → 单向 DAG✅ 无环 + 保住 Go 前置治理；代价：多一些部署角色
B去掉反向调用：Python 直连模型，Go 靠「下发配置 + 读 llm_call_log」间接治理✅ 无环、最省事；代价：不能「调用前」硬拦截（适合 M1–M2 起步）
C接受双向，但加护栏（独立连接池 / 超时背压 / 幂等）⚠️ 能跑但不优雅；必须能讲清为什么
面试点
「我最初的实现里 Go 既在 Python 上游（入口）又在下游（LLM 网关），同步双向会形成循环等待、有池耗尽死锁风险。所以我把它拆成 gateway、llm-gateway、algo 三个角色，让整个调用拓扑变成单向的 DAG。」 —— 这一句把你从「会写代码」拉到「懂分布式调用拓扑」。
本章一句话（可直接用于面试）
「Go 是控制平面（control plane），Python 是智能平面（intelligence plane）， 两者用 gRPC 解耦，运行态集中在 PostgreSQL，所以两边都是无状态的、可水平扩容的。」

5请求全链路时序（以「生成志愿方案」为例）

Go 侧动作分属三个角色：入口 / 会话 / HITL / 循环闸门 → svc-gateway；LLM 治理 → svc-llm-gateway；领域算法 → svc-algo（见 4.3 / 4.9）。

  1. 客户端发起Go POST /v1/plans + SSE 订阅；带 Idempotency-Key，网关鉴权、限流、生成 trace_id。
  2. 建会话Go Session 服务创建 session_id，写入初始输入；LangGraph 图启动，落第一个检查点。
  3. 交互采集（INTAKE 子图）LLMHITL ProfileAgent 经 svc-llm-gateway 调云模型，把自然语言解析成结构化画像（JSON Schema 约束）；随后确定性校验函数查缺 → 缺必要项就追问（interrupt + SSE 推送）→ 用户答完 resume → 再查缺……循环直到「全局必需」齐全（或到轮次上限 / 用户声明「不确定」）。
  4. 位次兜底Algo 若用户只给分数，RankConverter 按省份+年份查「一分一段表」换算位次。
  5. 暂停确认HITL 引擎进入 PROFILE_CONFIRM，SSE 推送画像卡片；用户修正后恢复，检查点续跑。
  6. 并行检索Python RetrieveAgent 发 gRPC：
    · 分支 A（结构化）：SQL 精确查询历年分数线 / 招生计划 / 选科要求
    · 分支 B（非结构化）：向量 + 倒排双路检索政策/招生章程，元数据过滤（省份/年份/科类）
    · RRF 融合 → Rerank → 返回带 source_uri 的 chunk
  7. 条件补问svc-gatewayHITL CHECK_CONDITIONAL 检查候选是否含「体检 / 单科 / 语种」要求且用户尚未提供 → 若有，走 BACKFILL_ASK 追问（interrupt/resume），答完回 PROFILE_CONFIRM；否则继续。
  8. 生成方案LLM StrategyAgent 基于检索结果生成冲/稳/保候选列表，每项携带证据引用 []。
  9. 硬约束校验Algo ConstraintChecker 用规则引擎过滤：选科不符、单科不达标、体检受限、批次错配 → 剔除并记录原因。
  10. 风险量化Algo ProbEstimator 用历史录取位次分布估计录取概率（分位数/核密度），输出概率与人话解释（解释由 LLM 写，数值由算法给）。
  11. 方案挑战LLM CriticAgent 审查：梯度是否合理？有无冲突？有无遗漏限制？返回问题清单。
  12. 循环闸门svc-gateway 若有问题且 loop < N → 回到步骤 8（生成方案，携带 Critic 意见）；否则继续。
  13. 志愿表优化Algo WishlistOptimizer 在平行志愿规则下做约束满足 + 排序优化（冲稳保配比、梯度平滑、避免同位次扎堆）。
  14. 生成报告LLM ReportAgent 输出方案说明 + 每项理由 + 数据出处 + 风险提示 + 免责声明。
  15. 幻觉校验svc-algoLLM Verifier 对每条事实性陈述检索原文比对：不一致则打回步骤 14（retry < M），一致则通过。
  16. 落库与返回Go 写结果、成本、耗时；关闭 SSE，返回最终结构化方案。
这条链路里，真正的难点在哪里
不是「调 LLM」，而是：检索路由的正确性（什么时候该查 SQL、什么时候该 RAG）、 两个循环的收敛（Critic 循环 + Verify 循环必须有上限且能收敛）、 检查点与恢复（HITL 暂停后能精确续跑）、成本闸门（多轮循环下 token 会放大）。

Intake 交互采集子图：画像 Schema 与两阶段采集

一句话
第一步既不是「让用户填表单」，也不是「开放聊天」，而是「Schema 驱动 + 确定性闸门 + 有限轮次」的交互采集。 这正是第 2 章那条论点的落点：传统工具假设用户知道自己要什么，而现实是用户是模糊的——采集阶段就是「把模糊的人问清楚」。

为什么要分两类字段（以及两阶段采集）

如果一上来就要求用户填「体检情况」，就正好犯了第 2 章说的毛病——逼用户填他自己都不知道要不要填的字段。所以分两段：

  • 第 1 段（全局必需）：只问必答的几项，拿到就往下走，去检索候选。
  • 第 2 段（条件必需，按需补问）：拿到候选后，只有当候选里确实有「体检 / 单科 / 语种」要求、且用户还没提供时，才追问那几项（即 CHECK_CONDITIONAL → BACKFILL_ASK）。

画像 Schema（闸门据此判断「够没够」）

类别字段说明
全局必需省份 / 年份 / 科类 / 分数 或 位次（至少一个） / 选科组合缺任一项都不能往下走
条件必需体检（色觉 / 视力）、单科成绩、外语语种、性别、往届应届、户籍 / 学籍（专项计划）只对「目标候选确实有该要求」时才需要
可推导（不必问）位次（分数 + 省 + 年 + 科类查一分一段表）、批次控制线由算法算出，少问用户
可选偏好地域 / 预算（学费）/ 专业兴趣 / 冲稳保倾向缺失不阻断，只影响排序与解释
闸门必须确定性（关键）
「信息够不够往下走」由一个校验函数判断（必需字段齐 + 合法），不许让 LLM 当闸门——否则不稳定、不可测。 追问的话术可以由 LLM 生成（自然、口语化），但问什么、够没够由 Schema + 校验函数决定。

为什么这些必须收——它们喂的是约束层

体检 / 单科 / 语种 / 性别不是「锦上添花的画像」，而是约束层（第 8 章 ConstraintChecker）的硬输入。 采集缺一项，约束层就可能放行一个本该被剔除的非法志愿——直接是事故。这就是闸门不能松的原因。

三个反模式（要避开）

  1. 做成「一张大表单」 → 退回传统填报工具，没发挥 AI 价值。
  2. 无限追问 → 必须有轮次上限 + 「不确定 / 跳过」出口（记录为低置信）。
  3. 让 LLM 判断「信息够不够」 → 闸门必须确定性。
面试点
「第一步我做成一个带确定性闸门的交互采集子图：Schema 定义必需字段，校验函数决定『够没够』，追问走 interrupt/resume。 而且分两段——先收全局必需，等拿到候选后，只对候选真正有要求的『体检/单科/语种』按需补问，避免一上来把用户问死。」

6.2 HITL 会话生命周期与超时管理

必须回答的问题：用户不回来了怎么办？
interrupt 暂停后，检查点和会话资源不能无限保留。必须有明确的生命周期管理，否则会造成存储泄漏和数据时效性问题。

会话状态机

状态含义超时 / 过期
ACTIVE图正在执行中单步超时 30s（LLM 调用）；整图超时 10min
WAITING_HITLinterrupt 暂停，等用户确认保留 30 分钟；超时后状态仍保留但标记为 EXPIRED
EXPIRED用户超时未响应检查点保留 7 天供恢复；用户重新发起则创建新会话
COMPLETED正常结束结果永久保留；检查点 30 天后归档
FAILED不可恢复错误检查点保留 7 天供排查

恢复时的数据时效性校验

用户 resume 时，如果距 interrupt 已超过 1 小时，必须重新校验：

  • 检索到的政策/章程是否仍在生效年份内（跨年场景）
  • 招生计划数据是否有更新（每年 6 月密集更新）
  • 若数据已过期 → 自动重新检索，不直接使用旧结果
实现要点
  • 定时清理：Redis key 过期 + PG 定时任务清理过期检查点
  • SSE 心跳：每 15s 发心跳，前端据此判断连接状态；断连后前端提示「点击重连」
  • 恢复入口：POST /v1/plans/{session_id}/resume，网关检查会话状态后决定是否允许恢复
  • 幂等保护：同一 session_id 的 resume 请求去重，防止用户多次点击导致图重复推进

7RAG 管线（离线 + 在线）

7.1 关键决策：结构化 vs 非结构化分流

这是本系统最重要的一个设计决策
分数线、招生计划、选科要求这类强结构化数据，绝不用 RAG 去「检索」——直接走 SQL 精确查询。
RAG 只用于政策文件、招生章程、体检规定这类非结构化文本。

原因：RAG 对精确数值（如「2025 年某校某专业最低位次 12345」）的召回与保真不可靠， 而这类数据错一个字就是事故。用 SQL 拿数值、用 RAG 拿规则语义，各司其职。

7.2 离线索引管线

① 采集考试院/阳光高考/院校官网；记录来源与抓取时间
② 解析HTML/PDF → 文本 + 表格；表格还原结构
③ 归一化省份/年份/科类/批次/专业代码统一编码
④ 分流结构化 → 关系表；文本 → 文档块
⑤ 切分政策按条款语义切分，带标题路径
⑥ 元数据抽取省份/年份/科类/文种/生效范围
⑦ 双写PG 表 + pgvector + tsvector 倒排
⑧ 质检抽样人工校验 + 覆盖率报告
切分策略（chunk）
  • 结构化数据：不切分，一个实体一行，字段即结构。检索走 SQL。
  • 政策/章程：按「条款」切分，保留父级标题路径（如「第三章 录取规则 > 3.2 平行志愿」），块大小 300–600 字，重叠 15%。
  • 表格类：转成 KV 文本 + 保留原表引用，且提供 table_id 供回溯。
  • 每块写入 source_uri + 抓取时间 + 生效年份，供引用溯源与时效判断。

7.2.1 数据采集质检（ETL QA）

⚠️ 数据错了，整个系统都白搭
爬来的数据如果有误（OCR 识别错、网站改版解析失败、人工录入错误），下游所有计算和推荐都会出错。 必须在入库前建立质检防线。

四层质检防线

层级检查内容触发时机失败处理
L1 · 格式校验 必填字段非空、数值类型正确、枚举值合法（省份/科类/批次编码） 解析完成后立即 拒绝入库，记录到 etl_error_log，告警通知
L2 · 范围校验 分数 0~750、位次 1~总人数、招生计划 ≥ 0、录取线 ≥ 批次线 L1 通过后 拒绝入库，标记为「待人工复核」
L3 · 趋势校验 同校同专业录取位次年际波动 < 30%；招生计划突变 > 50% 标记告警 L2 通过后，与历史数据对比 允许入库但标记 needs_review，在推荐时降低置信度
L4 · 抽样人工复核 每批次随机抽 5% 数据，人工比对原始文件 每轮 ETL 完成后 错误率 > 1% → 整批打回重做

异常检测规则（举例）

# 数值合理性
assert 0 <= admission_score <= 750
assert 0 < min_rank <= total_candidates
assert plan_count >= 0

# 趋势合理性（与上年对比）
if abs(this_year_rank - last_year_rank) / last_year_rank > 0.3:
    flag("位次异常波动", college_id, major_id, year)

# 逻辑一致性
assert admission_score >= batch_cutoff  # 录取线不应低于批次线
assert major.subject_req is subset of track.allowed_subjects  # 选科要求合法
实现要点
  • ETL 管线用 Python 脚本（pandas + 自定义校验器），独立于在线服务
  • 每轮 ETL 生成质检报告（JSON），记录通过率、异常条目、处理结果
  • 告警通道：错误日志写 PG + 可选推送（邮件/企业微信）
  • 数据版本管理：每次 ETL 记录 etl_run_id，可回溯到具体哪一轮入库

7.4 技术选型：为什么自建检索层（LlamaIndex / LangChain 的定位在哪）

结论
编排归 LangGraph，检索自建薄层压在 pgvector / tsvector 上。
LlamaIndex（以及 LangChain 的 retrieval 层）不是必需；要留，就只留在「离线解析 / 快速基线」当工具，别让它当 RAG 主干。
框架能给的本架构真正要的
快速把一堆文档变可检索结构化（SQL）/ 非结构化（RAG）分流
现成的 Index / Retriever / QueryEngine可控 hybrid：pgvector ‖ tsvector → RRF → rerank
大量向量库集成每条结果带 source_uri，供 Verifier 逐条比对
Reader / NodeParser 等摄取零件自定切分（按条款 + 标题路径，300–600 字，重叠 15%）
Response synthesis 自动合成强制引用 + 幻觉校验（不许框架「顺手帮你写一段」）
框架自带的 RAG 管线检索是被编排层调用的能力，不是框架的地盘
把它当主干，会在四个地方别扭
  1. SQL / RAG 分流被它挡着：本项目的核心决策是「数值走 SQL、语义走 RAG」，而框架的模型是「文本检索」——把分数线塞进去检索，是它最不该干、也最不擅长的活。
  2. 引用与幻觉控制要「露出来」：每条结论必须带出处、还要 Verifier 拿原文比对；用自动合成，citation 控不精细，最后还得拆开重写。
  3. 切分本来就要自己写：按「第 X 条 + 标题路径」切是定制逻辑，默认 splitter 做不到，你反正要写——那用它这层就意义不大。
  4. 会多出重叠的编排层：编排已用 LangGraph（见第 6 章）；再叠一个框架的 Workflow / QueryEngine，面试官必问「为什么两层、边界在哪」。

为什么
控制权全在自己手里、每一步都能解释——这正是第 15 章「护城河优先级」第 1、2 位（检索质量、验证器）要的东西。

  • 离线解析：PDF / HTML 读取可以用现成 Reader 省事，用完即弃。
  • 快速基线：想两天内先跑通一个「能查」的原型、验证数据质量，可以用它。
  • 零件级复用：Embedding / Reranker 封装可参考，但直接调 sentence-transformers 同样简单。
原则
用它的「零件」，不用它的「引擎」。

与本项目现状的关系

现有 GaokaoCompass 仓库用的是 LlamaIndex + ChromaDB + bge-large-zh-v1.5。把它定位为 bootstrap（引导原型），不是终态：

  • 到 M1 做 RetrievalService 时，逐步把「检索 + 合成」换成 pgvector / tsvector 自建层；框架若还留，只留在离线解析那段。

什么时候可以放心继续用它
① 只想快速出 demo、不追检索指标；② 数据是纯文本单一来源、不需要 SQL / RAG 分流；③ 不打算自己写 RRF / rerank / verifier。
—— 本项目三条都不命中。

7.5 存储选型：为什么 pgvector 够用（附中文全文检索的坑）

结论
目标架构里 ChromaDB 退役，PostgreSQL 一个库扛三件事（结构化 + pgvector 向量 + tsvector 全文）。
而且在这个项目里 DB 不是瓶颈，LLM 才是——DB 毫秒级，LLM 秒级，差两三个数量级。

为什么 PostgreSQL 一个库就够

PG 把三件事合并了：结构化数据（分数线 / 招生计划 / 一分一段）走关系表；向量检索走 pgvector；全文倒排走 tsvector + GIN。三个收益恰好都踩在本架构上：

  1. SQL 与向量同库：一个事务、一次连接、一套备份运维。
  2. 元数据硬过滤能 JOIN 结构化表：Chroma 只能按 metadata 过滤；PG 可直接 WHERE 省份=? AND 年份=?，甚至和录取线表 JOIN。这正是本架构「硬过滤优先」的落法。
  3. hybrid 天然可行：pgvector 与 tsvector 同引擎，RRF 融合前两路结果都在库里，少一个系统。
维度ChromaDBPostgreSQL（pgvector + tsvector）

结构化 + 向量同库❌ 割裂✅ 同库同事务，可 JOIN
全文 / BM25❌ 无原生✅ tsvector + GIN
元数据过滤基本强（SQL WHERE / JOIN）
运维多一套系统一套

迁移节奏
现在（bootstrap）继续用 Chroma 没问题——它已帮你验证了数据质量；到 M1 做 RetrievalService 时换 PG，Chroma 退役。判断标准：要不要 JOIN 结构化 + 要不要 hybrid + 要不要生产并发——本项目三条都要。

性能：三块分开看

负载说明
结构化查询（11M 行 CSV）单机 PG 处理千万~上亿行是常规；配好（province + year + category）复合索引后，按省份 + 年份 + 分数查录取线，典型单位数~几十毫秒。属于 PG 最擅长的等值过滤。
向量检索（pgvector）用 HNSW 索引（别用 IVFFlat，起步难调）；1024 维、几万~几十万 chunk 的规模下，查询通常 1~10ms。本项目规模对 pgvector 属小数据。
全文检索（tsvector）⚠️ 中文有坑，见下。
⚠️ 中文全文检索的坑（最容易被忽略）
PostgreSQL 内置全文检索是为空格分词的语言（英 / 法 / 俄）设计的。中文没有空格，默认 tsvector 分词效果很差——直接搜「平行志愿 录取规则」会不理想。三种解法：
  • 装 zhparser 或 pg_jieba 扩展（中文分词，最正统）；
  • 用 pg_bigm / pg_trgm 做子串 / 三元组匹配（简单、无需分词，召回偏宽）；
  • 或以向量为主、关键词为辅，keyword 只做粗过滤。
这个决定要早做，它直接影响 hybrid 里「倒排那一路」的质量。面试主动提「中文语料要上 zhparser」是加分点。
混合查询（filter + ANN）的坑
pgvector 支持「先按 WHERE 过滤再 ANN」，但过滤太狠时，近邻可能不够。缓解：给常见过滤维度（省份 / 年份）做部分索引（partial index），或先过滤再在子集里搜。pgvector 0.7+ 对「带过滤的近似搜索」更好，版本尽量新。
并发与内存
PG 能扛高并发，但要用连接池（pgbouncer）；HNSW 索引要常驻内存才快，本项目规模内存占用可控（几百 MB ~ 1~2 GB 级），想省内存可用 halfvec（本项目不必要）。

什么时候才该换「专用向量库」

满足任一，再考虑 Milvus / Qdrant：向量到亿级以上；需要几百 QPS 且 <10ms 稳定 SLA；需要 GPU 加速 ANN。本项目规模离这条线差 2~3 个数量级。第 14 章的 ADR 也是这么写的：亿级向量或高 QPS 时才迁 Milvus。

一句话
目标架构里 Chroma 退役，PG 一个库扛三件事，性能绰绰有余；真正要小心的是中文分词选型，其次才是向量索引调参。

8领域算法层（Go · 确定性代码）

这层是本项目的「护城河」——纯 LLM 方案做不出可靠结果，必须靠算法兜底。

模块职责方法
RankConverter分数 ↔ 位次 换算；跨年位次可比化 一分一段表查表 + 插值；同位次法/线差法；输出可比位次
ProbEstimator某院校专业录取概率 历史录取位次分布 → 分位数 / 正态 / 核密度估计；输出概率 + 置信区间 + 依据样本年份
ConstraintChecker硬规则裁决 规则引擎（规则表驱动）：选科匹配、单科要求、体检限报、性别限制、批次、学费上限
WishlistOptimizer志愿表排序与配比 约束满足 + 启发式搜索（贪心 + 局部搜索），最大化期望效用，约束冲稳保配比与梯度平滑
AdmissionSim平行志愿投档模拟 按「分数优先、遵循志愿」规则模拟投档，验证方案可行性
LLM 与算法的分工契约
交给 LLM交给算法
理解用户模糊偏好（「想离家近点」「偏工科」）位次换算、概率数值
生成候选、写理由、写风险提示规则合法性裁决
批评方案、发现语义冲突志愿表排序与配比优化
把数值结果翻译成人话投档可行性模拟
一句话：LLM 不许算数，算法不许编话。

为什么这层放 Go（以及它在什么情况下可以放 Python）

先厘清原则：约束是「离 LLM」，不是「用 Go」
核心原则是「LLM 不许算数，算法不许编话」——即确定性代码必须与 LLM 分离。 它没有规定这层必须是什么语言。所以「算法必须 Go」是个过强的说法；真正被约束的是「算法不能躺在 LLM 里」。 （顺带：本章说的「护城河」是算法本身——位次法、概率模型、约束满足、投档模拟——与语言无关。）

放 Go 的四个理由

理由说明
性能（CPU 密集）WishlistOptimizer（约束满足 + 启发式搜索）、AdmissionSim（大规模模拟）是「循环密、分支多」的计算；Go 紧循环通常比 Python 纯循环快 10–100×。查表 + 插值这种轻活 Python 也够。
并发扇出「对 N 个院校并行估概率 / 并行校验约束」用 goroutine 又便宜又简单；Python 在 CPU 密集下受 GIL 拖累，要上多进程，摩擦更大。
解耦与可测试确定性代码单独成层，能与 LLM 层分开单测、分开回归、分开审计——正是「数值可解释、可复现」要的。
用不上 Python 的生态算法只需「纯计算 + 读 SQL」，不需要 LLM / 向量 / 数据科学生态——Python 的最大优势在这里发挥不出来，放 Python 无天然收益。（算法作为独立服务 svc-algo，只需「纯计算 + 读 SQL」，与 LLM 治理解耦。）

反方：Python 确实更强的地方（别装看不见）

  • 概率估计（ProbEstimator）：Python 的 scipy.stats（分布 / 分位数 / KDE）、sklearn 更厚。Go 侧是 gonum，够用但没那么顺手——这是唯一有正当理由放 Python 的模块。
  • 原型速度：约束表、启发式规则用 Python 迭代更快。
  • 少一跳：算法若在 svc-orchestrator 内部，就是本地函数调用，没有 gRPC 网络跳。
结论与建议
  • 推荐（本方案）：算法统一放 Go——对最重的两块（优化 + 模拟）性能 / 并发优势真实，不需要 AI 生态，还能与后端经验对上。
  • 但承认这是选择：只做 MVP、算法还不重时，全放 Python 也成立，反而更快。
  • 可折中：只把 ProbEstimator 抽到 Python（用 scipy），其余留 Go——完全合理。
  • 不建议：为算法单起一个 Python 服务（多一个部署、多一份运维）；既然同语言，不如并入 svc-orchestrator 当内部模块。
面试备答：算法为什么不用 Python？
「原则是『确定性代码和 LLM 分离』，不是『算法必须 Go』。我放 Go 是因为这几类算法正好是 CPU 密集 + 高并发扇出 + 不需要 AI 生态，Go 在这三点都更合适，也和我的后端经验对得上。 统计部分（概率估计）我确实评估过——Python 的 scipy/sklearn 更顺手；但它不是瓶颈，为了一致性和可测试性我统一放 Go，后面若要上更复杂的统计模型，我会把那一块单独抽出去。」

9.2 缓存与队列（Redis）

  • 检索缓存：query_hash + filters 为键，政策类 TTL 长、分数线类 TTL 短。
  • LLM 结果缓存：相同 prompt_hash 直接命中，省钱且稳定。
  • 长任务队列：批量生成（如整班方案）走队列异步执行。
  • 限流与预算：令牌桶 + 每会话 token 计数器。

缓存失效策略（关键：政策数据更新时不能命中旧缓存）

缓存类型Cache Key 组成TTL失效触发
检索结果 hash(query + filters + data_version) 结构化数据 24h；政策文本 7d 数据更新时 data_version 递增 → 旧 key 自然失效
LLM 输出 hash(role + model + prompt + data_version) 方案生成类 12h；解释类 24h ① data_version 变更 → 主动删除相关 key
② 模型版本切换 → 清空该 role 缓存
算法结果 hash(algo_type + params + data_version) 位次换算 30d；概率估计 7d 历史数据更新时失效
⚠️ 为什么 cache key 必须带 data_version
如果只用 prompt_hash 做 key，政策更新后（如某校新增选科要求），旧回答仍在缓存中被命中 → 推荐了不合规的志愿 → 事故。
data_version 在每次 ETL 完成后递增，所有缓存 key 都带上它，数据更新时旧缓存自然无法命中。

10服务契约（proto 草案）

单一 .proto 事实来源，Go 与 Python 各自生成，避免接口漂移。

// ============ 通用 ============
message Trace {
  string trace_id   = 1;
  string session_id = 2;
  string node       = 3;   // 哪个 Agent 节点发起
}

// ============ 检索服务（Python 侧实现） ============
service RetrievalService {
  rpc Retrieve (RetrieveRequest)  returns (RetrieveResponse);
  rpc Index    (stream IndexChunk) returns (IndexAck);      // 离线写入
}

message QueryFilters {
  string province      = 1;   // 必填，硬过滤
  string year          = 2;
  string subject_track = 3;   // 物理类/历史类…
  string batch         = 4;
  repeated string college_ids = 5;
  repeated string major_codes = 6;
}

message RetrieveRequest {
  Trace        trace       = 1;
  string       query       = 2;
  QueryFilters filters     = 3;
  int32        top_k       = 4;
  bool         with_rerank = 5;
  bool         need_structured = 6;   // true=走 SQL 精确路径
}

message RetrievedChunk {
  string chunk_id    = 1;
  string doc_id      = 2;
  string text        = 3;
  double score       = 4;
  string source_uri  = 5;
  string source_type = 6;   // policy | admission | regulation
  string effective_year = 7;
  map<string,string> meta = 8;
}

message RetrieveResponse {
  repeated RetrievedChunk chunks = 1;
  repeated StructuredRow  rows   = 2;   // 结构化结果（分数线等）
  string route = 3;                     // sql | rag | hybrid，便于调试
}

// ============ 推理服务（Python 侧实现） ============
service InferenceService {
  rpc Chat   (ChatRequest) returns (ChatResponse);
  rpc Stream (ChatRequest) returns (stream ChatDelta);
  rpc Embed  (EmbedRequest)  returns (EmbedResponse);
  rpc Rerank (RerankRequest) returns (RerankResponse);
}

message ChatRequest {
  Trace  trace      = 1;
  string role       = 2;    // profile|strategy|critic|report|verify → Go 侧据此路由模型
  repeated Msg msgs = 3;
  string json_schema = 4;   // 非空则强制结构化输出
  double temperature = 5;
  int32  max_tokens  = 6;
  int32  timeout_ms  = 7;
}
契约里的两个巧思
  • Trace 全字段透传 → Go 与 Python 的 trace 能在同一棵树里合并，这是「跨语言可观测」的关键。
  • role 由 svc-llm-gateway 指定模型 → 路由与成本控制在 svc-llm-gateway；svc-orchestrator 只负责「何时调、调什么内容」，不碰 key 与计费。

10.1 API 版本策略

版本规则
  • URL 路径版本：/v1/plans、/v2/plans——HTTP API 用路径前缀区分版本
  • proto 包版本：api/gateway/v1/、api/gateway/v2/——gRPC 用包路径区分
  • 向后兼容：新增字段用新编号（不改已有字段编号）；废弃字段标 deprecated 但保留至少 2 个版本周期
  • 破坏性变更（删字段、改类型、改语义）→ 必须出新版本（v2），旧版本保留 ≥ 3 个月
变更类型是否破坏性处理方式
新增可选字段否直接改，升 minor 版本
废弃字段（标记 deprecated）否保留，下个版本移除
删除字段 / 改字段类型是新建 v2 目录，旧版本保留过渡期
改接口语义（如返回结构大变）是新建 v2，旧版本保留过渡期
起步阶段
当前全部在 v1，不需要过度设计。只需遵守一条纪律：新增字段永远用新编号，永远不删已有字段。等真正需要破坏性变更时，再拆 v2。
与调用拓扑（4.9）保持一致
拆成 DAG 后，云端 LLM 的 Chat / Stream 由 svc-llm-gateway（Go）实现并暴露 gRPC 供 svc-orchestrator 调用，key 只留在 svc-llm-gateway。
因此 Python 的 InferenceService 收敛为本地模型的 Embed / Rerank（可选本地小模型），不再对外提供云 Chat——否则又会引入反向调用、破坏 DAG。

L2 · 契约测试 proto 接口兼容性：请求/响应格式不变 protoc-gen-go + grpcio-tools 生成后编译检查；可选 buf breaking proto 变更时 接口向后兼容、不破坏已实现的 client/server
L3 · 集成测试 单服务 + 依赖（DB/Redis）：API 端到端、gRPC 调用链 docker-compose.test 起依赖 + 测试容器 每次 PR 服务能启动、DB 迁移正确、gRPC 调用通
L4 · 端到端评测 全链路：用户输入 → 最终方案 golden set + 指标计算（recall、faithfulness、幻觉率） 每次 PR（CI 门禁） 业务质量不回归（见 11.2）

部署阶梯：L0 → L3（OrbStack 属于哪一级）

先纠正一个概念
OrbStack 不是「部署目标」，它是本机上的「本地容器运行时」（比 Docker Desktop 快、省资源，还能开 Linux 机器）。 「部署到 OrbStack」准确说是「用容器在本地把整套跑起来」——属于 dev / 验收，不等于对外发布。
级别环境目的里程碑
L0本地直跑（go run / uvicorn + 本机 PG/Redis）开发最快，免反复 build打通一条链
L1OrbStack + docker-compose验证「整套能一起跑」、环境一致、可复现一条命令起全栈
L2单台云 VPS + docker-compose公网演示、面试可点链接有可用 URL
L3k8s（可选）展示 HPA / 滚动发布（平台岗才需要）非必需
和「环境策略」的对应
L1 ≈ 本地开发；L2 ≈ 演示 / 面试；L3 ≈ 生产演练。 对求职项目：做到 L1 + 一个 L2 最小演示就够，L3 看岗位。要点是尽早写 compose——「能一键起」是让别人复现的门槛，也是面试加分。

云上最小方案（L2）

  • 1 台 VPS（Ubuntu，≥ 4GB RAM）→ 装 docker + compose
  • 同一份 compose（compose.prod 变体）→ docker compose up -d
  • 最前面加 Caddy：自动 HTTPS + 域名 + SSE 不缓冲
  • 数据用子集（1–2 省 × 2–3 年），别塞 11M 行
  • 入口加限流 + Budget Guard——公网暴露一个能烧 LLM 预算的接口很危险，正好用你自己的成本闸门挡
  • 云 LLM 用 API，别在云上跑本地模型（云 GPU 贵）
部署踩坑清单
  • SSE 被代理缓冲：Caddy/nginx 必须关响应缓冲，否则流式被「攒着一次吐」。Caddy 默认 flush；nginx 要 proxy_buffering off。
  • PG 镜像要带 pgvector + 中文分词：用 pgvector/pgvector 镜像拿 pgvector；zhparser / pg_jieba 要自定义镜像（早做，最容易卡）。
  • 数据子集：镜像小、启动快。
  • 密钥不入库：.env / secrets 注入；公网必须限流防刷。
  • 内存：sentence-transformers（bge）+ PG + 观测都吃内存；svc-orchestrator 镜像里预下载模型。

可观测：L2 就能做（不必等 k8s）

能，而且应该做——第 11 章把可观测当亮点，L2 正是把它落地的地方。三种方式，按资源选：

方式做法取舍
A · 全自托管compose 里加 OTel Collector + Prometheus + Grafana（+ Tempo/Loki）可控、全在内网；但吃内存、要自己维护
B · 混合（推荐）本地跑 OTel Collector，把 metrics / traces push 到 Grafana Cloud 免费层（OTLP 端点）省资源、有公网面板可分享 / 截图

  • 指标：Go 用 prometheus client、Python 用 prometheus_client → Prometheus / Grafana Mimir。

  • 成本曲线：llm_call_log 表 → Grafana 的 Postgres 数据源直接读 → 单会话成本 / 缓存命中 / 循环轮次。这项甚至不需要 Prometheus。

面试价值

最小可行备份脚本（L1/L2 环境）

#!/bin/bash
# deploy/backup.sh — 每日 cron 执行
BACKUP_DIR="/data/backups/$(date +%Y%m%d)"
mkdir -p "$BACKUP_DIR"

# PG 全量备份
docker exec postgres pg_dump -U gaokao -F c gaokao_db > "$BACKUP_DIR/pg_dump.sql.gz"

# Redis RDB 拷贝
docker exec redis redis-cli BGSAVE
sleep 5
docker cp redis:/data/dump.rdb "$BACKUP_DIR/redis.rdb"

# 清理 7 天前的备份
find /data/backups -maxdepth 1 -mtime +7 -exec rm -rf {} \;

echo "[$(date)] Backup completed: $BACKUP_DIR"
恢复流程
  1. 新建 PG 容器 → pg_restore 导入最近备份
  2. 新建 Redis 容器 → 加载 RDB
  3. 对象存储从异地副本同步
  4. docker compose up -d 启动全部服务
  5. 验证健康检查 → 恢复完成
全程目标 RTO < 1 小时（单机环境）。

边界铁律（让「单仓」看起来是「干净」而不是「揉在一起」）

  • 契约是唯一的缝：服务之间只经 api/ 生成的 client / server 通信。
  • 禁止跨服务 import：cmd/gateway 不能 import internal/llmgw 或 internal/algo；只能调它们的生成 client。
  • 共享层只放基建：internal/pkg 只有 store / obs / middleware / errors，不放跨服务的业务逻辑。
  • 目录名 = 服务名：四个位置一眼可数，且与第 4 章的架构图一一对应。
  • 可选加固：CI 里用 go-arch-lint / depguard 把「禁止跨服务 import」变成机器保证。
ADR：为什么用 monorepo（而不是 4 个仓）
  • proto 单一来源：契约要 Go/Python 同时生成，单仓才能一次改、两边同步，不会契约漂移。
  • 原子提交：一个需求常同时动契约 + 两端，单仓一个 PR 完成；多仓要各自发版对齐。
  • 单人可复现：一次 git clone 即可 docker compose up；对面试官是最低门槛。
  • 边界靠契约强制，不靠仓库隔离：服务数 ≠ 仓库数；仓库跟着「团队 / 发布边界」走，单人项目就是 1 个。
多仓只在「多团队、独立发布节奏、权限隔离、超大代码库」时才划算——本项目都不成立。
面试话术（若被问「为什么不用多仓 / 会不会揉在一起」）
「项目单人维护，多仓的收益（团队隔离、独立发布）我用不上，成本（版本对齐、契约漂移）却实打实。所以我用单仓，但用 api/ 把一个仓切成 4 个边界清晰的服务——边界靠契约强制，不靠仓库隔离。
判断『揉没揉』看的是契约清不清、边界硬不硬、目录对不对得上架构图，不是仓库数量。」

15决策记录：自研编排 vs 现成框架

结论（TL;DR）
编排主干用 LangGraph，不写通用状态机引擎。
自研只投在框架之上的差异化切片：规则引擎、位次/概率算法、成本路由网关、检索分流器、验证器。

15.1 这是两个问题，答案相反

「自研好还是用 LangGraph 好」实际是两个问题：

  • 技术账：哪个更省事、更可靠？
  • 求职账：哪个更利于拿到「Agent 应用开发工程师」的 offer？

这两个答案恰好相反，必须分开看——分开之后结论才清晰。

15.2 技术账：框架白送你的 vs 你要亲手重造的

LangGraph 开箱提供自研的话你要自己写
持久化检查点（Postgres / SQLite saver），进程挂了能续跑状态快照原子写；并发节点写同一状态时的合并语义
interrupt / resume（人工介入的标准实现）暂停时序列化整个运行态，恢复时精确还原
时间旅行：从任意检查点重放恢复时哪些节点重跑、哪些跳过（幂等语义）
流式输出（token 级、节点级、自定义事件）多节点并发时事件顺序的一致性与前端可消费性
节点级重试策略重试与副作用的隔离（LLM 调用、写库不重复）
并行节点 + map-reduce调度器与上下文取消
子图组合（subgraph）子流程的状态隔离与传参
状态 reducer（并发写状态的合并语义）自定义合并逻辑
工时估算
一个人把上表右列写到生产可用，保守估计 4–8 周，且是纯投入、不产出业务价值。这 4–8 周本可以用来把 RAG 质量、验证器、评测体系做扎实。
编排引擎的难点集中在持久化 + 中断恢复 + 并发一致性——这三样恰恰是别人已经解决、你重造只会踩坑的东西。
如果你真正的诉求是 durable execution
不要手搓。直接用 Temporal（Go 原生，重试 / 重放 / saga 成熟），在它上面套 Agent 循环。面试里说得出这句，比说「我自己写了个状态机」更显功力。LangGraph 的 checkpoint 也是同一思路的轻量版。

15.3 求职账：入场券 vs 加分项

会 LangGraph自研引擎
岗位 JD 要求 大量 JD 直接写「熟悉 LangGraph / LangChain / AutoGen / CrewAI」——这是入场券 几乎没有 JD 要求「自研过编排引擎」
缺失的后果 一面被问「LangGraph 用过吗」，答「我自己写了一个」，面试官第一反应是「他是不是不了解这个生态」→ 可能直接出局 只是不突出，不会出局
投入产出比必须拿拿完入场券之后再争
顺序不能反
先自研 = 冒着没有入场券的风险去争加分项。正确顺序是：先拿入场券，再用差异化能力加分。

15.4 决定：分阶段，别一次定终身

阶段做什么目标
M1–M3 用 LangGraph 搭主干图（Profile→Retrieve→Strategy→Constraint→Risk→Critic→Optimize→Report→Verify）；把进阶用法用足：interrupt/resume 做 HITL、Postgres saver 做断点续跑、subgraph 做 Critic 循环、reducer 做状态合并 拿到入场券 + 能跑的系统 + 评测基线
M4–M5 自研「框架之上的差异化切片」：规则引擎、位次换算与概率估计、成本感知 LLM 路由网关、检索分流器、验证器 把 Go 优势落到项目里，形成护城河
M6（可选） 用 Go 写轻量编排器跑同一张图，与 LangGraph 做基准对比，产出博客 「两者都懂 + 有数据」的最强求职姿态；时间不够就砍

15.5 两种落法（结合 Go + Python 架构）

路线分工优点缺点
A（推荐） Python：LangGraph 编排 + 推理；Go：Gateway/SSE、算法域、LLM 路由网关、验证器、评测触发 最快拿到入场券；Go 承担「框架之上」的工程，价值清晰 编排逻辑在 Python，Go 不在核心执行路径上——但差异化本来就不该靠「谁跑的图」
B（次选） Go：自研编排；Python：只做推理 最大化 Go 主导权，叙事最完整 多花 4–8 周写引擎，且要自己兜住持久化 / 恢复 / 并发的坑
选 A。现在最缺的是时间，不是技术深度。

15.6 护城河应该投在哪（按优先级）

  1. 检索质量（召回、时效过滤、分流通路正确性）——决定系统靠不靠谱
  2. 验证器 + 引用溯源——决定幻觉率，本场景的生死线
  3. 评测体系（golden set + CI 门禁）——大多数人没有，你有就是碾压
  4. 成本与并发治理（路由、缓存、预算、闸门）——发挥 Go 优势的主场
  5. 领域算法（位次 / 概率 / 约束 / 优化）——别人做不出来的硬东西
  6. 编排引擎本身 —— 排最后，因为别人已经做得比你好
提醒
自研状态机排在优先级 6，而直觉常常想把它排到 1 或 2。这就是本章存在的意义。

15.7 什么情况下应该反过来选自研（边界条件）

满足以下两条以上，自研才成立：

  • 目标岗位明确不要求主流框架（少见，部分基础架构岗如此）
  • 有 4–8 周冗余时间，且愿意承担引擎出 bug 拖垮项目的风险
  • 项目定位就是「编排引擎本身」（如要做开源框架），而非业务应用
  • 已在真实项目里深度用过 LangGraph，能说清它的具体不足（「我觉得不够灵活」不构成理由，要能说出具体场景与复现路径）
不符合以上条件，先自研就是拿求职时间去赌技术洁癖。
一句话记住：LangGraph 是你要买的入场券，自研是入场之后才争的奖杯。先把系统做对，再证明你能看懂框架的边界——后者靠的是成本治理、检索分流、验证器、评测体系，不是重写一遍状态机。

16降级与故障处理

故障检测降级策略
LLM 超时/限流Gateway 超时计数节点级重试（指数退避）→ 换备用模型 → 用规则模板兜底并标注「生成质量降级」
检索无结果召回数为 0 或低于阈值放宽元数据过滤 → 提升 top_k → 明确告知「无可靠数据，不予推荐」
Critic 循环不收敛达最大轮次或无进展强制进入优化阶段，输出方案并显式标注未解决问题
版本幻觉打回超限Verify 失败次数 ≥ M剥离无引用段落，仅输出可溯源内容 + 人工提示
成本超预算Budget Guard截断后续循环 → 返回当前最优结果 + 说明
下游 Python 服务不可用gRPC 健康检查熔断 + 缓存结果回放；无缓存则明确失败，不假装成功
一条硬规则
宁可明确报错，也不许编造数据。志愿场景里，「没有可靠数据」是一个合法且必须被明确表达的结论。 这种「不假装成功」的设计，本身就是面试里很好的技术品味证明。

17安全与合规

数据合规仅采集公开数据；记录来源与抓取时间；遵守站点条款；不采集个人信息。
隐私保护用户输入最小化；日志脱敏；不持久化身份证/手机号等敏感字段。
Prompt 注入RAG 内容视为数据；显式分隔与转义；工具调用白名单；SQL 全参数化。
输出安全禁止承诺录取；强制风险提示与免责声明；敏感建议加人工确认。
在 README 中单列「合规与免责」章节，注明数据来源、使用边界与免责条款。 这既是法律要求，也是向面试官展示「你知道真实业务要面对什么」。

阶段架构增量验证目标

（如果此时你有余力，再用 Go 重写编排器并与 LangGraph 做基准对比，那是加分项，不是必选项。）
