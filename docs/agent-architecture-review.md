# Agent 架构审查与端到端流程建议

审查对象：[agent-architecture.html](agent-architecture.html)。

本文依据原文、当前工作区源码、proto 和仓库 schema 进行静态审查，包含独立审查结论及实现对照。未运行数据库、在线模型或整套系统；不代表生产验收或法律合规认证。本次只新增本报告，未修改原 HTML、业务代码、接口或数据库。

文中的“现状”指当前源码；“原文”指被审查的 HTML；“建议”指尚待实施的目标设计。接口存在、注释描述、路线图计划，不等于功能已经实现。原文行号用于定位本次审查版本，后续编辑后可能变化。

阅读指引：第 2 节看当前能力，第 3–4 节看职责与问题，第 7 节看逐步调用流程，第 8 节看异常/修改，第 10 节看实施顺序和验收。

## 1. 总体结论

**四服务方向可以保留，不需要推翻重做，也不需要继续增加 Agent 微服务。当前主要问题是职责与状态边界没有闭合，部分安全目标被降级路径绕过，且原文已与实际 algo 契约脱节。**

值得保留的设计：
- LLM 处理语义、偏好归纳和表达；确定性代码处理数值、资格和发布条件。
- 结构化查询与政策 RAG 分工，PostgreSQL + pgvector + 全文检索作为起点。
- LangGraph 承载有界循环和人工中断，服务之间保持单向业务调用。
- 先收全局必要信息，再按候选要求补问条件信息。
- 原文已经考虑 HITL 超时、缓存版本和 ETL 质检；需要完善它们之间的连接，而不是另造一套同名机制。

优先调整的五件事：
1. 图的下一步、补问和循环统一由 orchestrator 决定，gateway 不遥控图内业务。
2. 以当前 `EstimateProb → OptimizeWishlist` 为算法主线，不能继续按“LLM 先编学校、算法再逐校算概率”接线。
3. 将任务执行与 SSE 连接分离，明确持久任务、具体中断、执行互斥、恢复幂等和结果落库。
4. 把当年权威资格规则、数据版本、三类证据接成闭环；未知不能当通过，预算不足不能跳过门禁。
5. 先完成受控的单方案闭环，再增加 Critic、多轮策略及性能扩容。

### 1.1 问题分类与优先级

- **原文矛盾**：同一职责或状态在不同章节有互斥描述。
- **设计缺口**：目标合理，但缺少让目标成立的协议、状态或数据链路。
- **实现差距**：原文是目标，代码尚未完成，不能据此宣称当前系统具备能力。
- **表述过强**：把估算、语言偏好或框架能力说成确定保证。
- **P1**：接入真实推荐用户前应解决；不是说当前未上线的桩代码已经造成生产事故。
- **P2**：应在对应功能开发前统一，防止集成返工和误导使用者。

因此，目前可明确讨论的是“已经实现的算法服务 + 待接通的 Agent 链路”，不是已经运行完整的多 Agent 推荐系统。之前算法阶段的完成状态不应因为本次审查而被重置；后续工作主要在其上接线和补充明确缺失的能力。

### 2.1 必须按实际口径描述 algo

1. 当前范围是湖南、物理类/历史类、本科批及合法 3+1+2 组合。请求明确给报考年，不按机器日期猜测哪年数据可用。
2. 候选单位是**院校专业组**。在固定省/年/科/批范围内，组键是 `UniversityCode + MajorGroup`；跨请求存储还必须带完整适用范围和数据版本。
3. `EstimateProb` 已包含分数换位次、候选生成、选科过滤、历史与计划查询、`weighted_hit` 概率及冲稳保分档。
4. `EstimateProb` 不接受任意目标院校列表。不能先让 LLM 自由生成学校，再假设该接口可逐一给它们补概率。
5. `CheckConstraints` 目前主要实现选科；它的注释列出体检、单科等，不代表已有这些输入字段和规则实现。
6. `OptimizeWishlist` 消费已有 `CandidateWithProb`，做效用、配比、排序和保底处理，不重查位次或重新估计概率。
7. 概率是历史加权命中估计，不是原文所述正态/KDE，也没有当前可调用的置信区间接口。
8. `slip_rate = Π(1−pᵢ)` 是独立性假设下的近似；`expected_satisfaction` 是效用均值，不能包装成真实录取保证或经过校准的满意度概率。
9. `safe_count` 是达到保底概率阈值的数量，不是全部“保”档数量；`safe_guard_ok=false` 是成功响应中的告警，不是 RPC 失败。
10. 当前候选骨架和专业明细主要来自上一年录取数据，再以报考年招生计划筛组。它适用于历史估算，不足以证明当年所有专业均可报。

证据：[recommend.go](../internal/algo/biz/recommend.go)、[constraint.go](../internal/algo/biz/constraint.go)、[optimize.go](../internal/algo/biz/optimize.go)、[candidates.sql](../internal/algo/data/queries/candidates.sql)。

## 3. 服务划分与数据所有权建议

### 3.1 保留四个服务，收紧每个服务的职责

| 服务/模块 | 应负责 | 不应负责 | 状态和数据责任 |
|---|---|---|---|
| svc-gateway | 用户身份、访问控制、入口限流、协议校验、命令转交、SSE/查询呈现 | 解析候选资格、判断图下一节点、Critic 回边、决定放过验证 | 拥有接入身份上下文；会话和 run 的业务状态以 orchestrator 为准 |
| svc-orchestrator | 意图路由、完整画像、LangGraph、补问/确认、图重试、候选与证据组织、报告和发布门禁 | 自行编造概率、另写一套候选 SQL 口径、绕过模型预算直连供应商 | 会话画像版本、run、interrupt、检查点、候选快照、证据包、结果、事件的唯一业务写入方 |
| svc-algo | 位次、候选池、确定性规则、概率、效用与优化；后续承接扩展资格规则 | 文本追问、对话状态、云模型调用、SSE | 读取已发布结构化数据/规则；返回可复核的算法产物，不推进 run |
| svc-llm-gateway | 模型白名单、角色路由、调用前预算、缓存、供应商重试、调用账本 | 决定用户是否具备资格、图的下一步、回调 orchestrator | 预算预占和结算账本的唯一写入方；向编排返回结构化结果和使用量 |
| orchestrator 内 RAG 模块 | 适用范围过滤、文档双路检索、融合、重排、证据定位 | 把未召回限制当“无限制”、用文本检索替代数值查询 | 读取已发布文档索引；保存当前 run 的证据引用 |
| 离线 ETL/审核模块 | 抓取/导入、清洗、身份映射、规则审核、切分/索引、质量验证、版本发布 | 在用户在线请求中批量导入、直接覆盖正在使用的发布版本 | 公共资料与规则的写入方；通过发布清单交付在线只读数据 |

“Session 服务”“Verifier”“Budget Guard”在此分别是内部模块，不自动意味着新增网络服务。执行 worker 可以是 orchestrator 的独立进程角色，仍归同一业务服务。

### 3.2 调用方向

```text
客户端 ──HTTP 命令/查询、SSE──> gateway
                                   │
                                   └──gRPC──> orchestrator
                                                ├──gRPC──> algo ──读──> 发布数据/规则
                                                ├──gRPC──> llm-gateway ──> 模型供应商
                                                ├──本地──> RAG / Embedding / Rerank
                                                └──读写──> run / 状态 / 证据 / 结果 / 事件
离线 ETL / 规则审核 ──发布──> PostgreSQL 中的不可变版本与索引
```

- gateway 主动订阅 orchestrator 事件；事件经既有响应流返回，不需要 orchestrator 反向发起 RPC 回调 gateway。
- 服务依赖是 DAG，LangGraph 内部允许有界循环，两者不矛盾。
- 单向依赖便于控制故障传播，但“同进程双向调用必然死锁”不成立；死锁取决于持锁等待、执行器/连接池饥饿等具体条件。
- Go/Python 是当前工程选择，不是“只有 Go 能治理、只有 Python 能编排”的技术定律。
- 初期共用一个 PostgreSQL 可以接受，但业务表写入权必须清楚。不要让 gateway、worker 同时覆盖 `chat_session.status/profile`。
- 本地 Embedding/Rerank 有 CPU/GPU、内存和加载成本；从异步 RPC 事件循环移入有界执行池，离线索引与在线推理隔离资源。

## 4. 详细问题与修改建议

### P1-01：硬规则只有消费端，没有完整的生产与发布链路

- **类型/位置**：设计缺口。原文 §7，1024–1043 行；§8，1318–1319 行；§9，1394–1401 行。
- **问题**：RAG 收录了章程，但确定性规则引擎需要结构化规则。文档未闭合“条款 → 规则 → 审核 → 生效 → 执行”链路。
- **影响**：检索没找到体检限制，可能被错误理解为学校没有限制；只保证 ETL 格式正确，不能保证规则语义正确。
- **建议**：规则记录适用省/年/科/批、组/专业、比较条件、所需用户字段、效力范围、证据位置、审核状态和发布版本。LLM 可以辅助抽取，不可直接发布。判定至少区分 `PASS / FAIL / UNKNOWN`；UNKNOWN 另带“用户字段缺失/规则覆盖不足/条款冲突”的原因。
- **验收**：缺少规则覆盖或存在冲突时，不得发布“资格已通过”的方案；允许展示待核实资料，但不能混入已通过候选。

### P1-02：必需字段与“到上限就低置信继续”互相冲突

- **类型/位置**：原文矛盾并已影响图骨架。原文 §6，951–974 行；当前 `route_after_intake` 在六轮后放行。
- **问题**：省、年、科、成绩、选科是算法调用前提，不是置信度高低问题。当前 `TypedDict` 也不是运行时输入校验。
- **建议**：全局必要字段缺失或非法时停止个性化推荐，或经用户选择转一般问答；条件字段缺失只影响需要它的候选；可选偏好才允许采用明确默认值。追问轮数只在实际产生新问题时增加，不能靠无用户输入的节点自循环累加。
- **验收**：缺省份/年份/成绩、非法选科、用户选择“不确定”等情况，不得因轮次耗尽而进入最终推荐。

### P1-03：降级、循环上限可能绕过正确性门禁

- **类型/位置**：设计缺口。原文 §5，832 行；§16，2208–2218 行。
- **问题**：“返回当前最优”“删除无引用段落”不能排除有引用但引用错误、资格不符、版本混用等问题。
- **建议**：所有成功发布出口统一经过资格、版本、关键事实和结构校验。预算/循环耗尽只能返回同一画像与版本下已验证的结果，或明确失败/资料查询结果；不得把未验证草稿变成正式方案。
- **验收**：注入错误概率、错年份引用、非法候选后，即使超预算也必须阻断。`safe_guard_ok=false` 属于风险告警，可在资格与事实均通过后输出带显著警示的参考结果，但不得标成“保底达标”。

### P1-04：检索不足时放宽硬过滤会改变问题本身

- **类型/位置**：原文降级风险。§7，1141–1147 行；§16，2209 行。
- **问题**：放宽报考省、年、科、批次，不是在改善召回，而是在引入不适用证据。
- **建议**：只调整查询措辞、召回数量、软偏好和检索通道。全国政策、持续有效条款通过显式适用范围继承纳入，不机械要求所有政策 `year == 报考年`；但不能用上一年章程冒充当年资格规则。
- **验收**：找不到本年院校条款时，返回证据不足和官方查询指引，不静默替换成年份相邻的资料。

### P1-05：“每条结论溯源到原文”无法验证算法派生数值

- **类型/位置**：表述过强与设计缺口。原文 §1，150 行；§5，827–832 行；§8，1310–1315 行。
- **问题**：录取概率和优化效用本来就不存在于章程原文。仅让另一个 LLM 判断引用，不等于数值正确或零幻觉。
- **建议**：分三类证据：文档事实绑定原文片段；结构化事实绑定行身份/字段/版本；派生事实绑定输入快照、样本、算法与参数版本、输出。数字优先由结构化模板渲染，确定性比较；LLM 只辅助文本蕴含检查。
- **验收**：数值或单位被报告改写、引用指向错误条款、样本年份不一致时，验证必须能单独报错。

### P1-06：隐私目标与健康画像、永久结果保存冲突

- **类型/位置**：原文矛盾。§1，158–163 行；§6，952、996 行；§17，2227–2228 行。
- **问题**：不收身份证/手机号，不代表不处理个人信息；体检、健康状况等具有敏感性。“不采集任何敏感信息”与功能目标不能同时成立。
- **建议**：区分公共资料采集和用户数据处理。条件信息最小化、按需明确告知和取得必要同意、分级授权、限期保存及可删除；健康细节默认不进入云模型、共享缓存、完整 prompt 日志或 trace。可向报告模型提供脱敏后的规则结论。
- **验收**：用户清除数据后，画像、检查点、结果、缓存及关联日志按既定策略处理；备份恢复不得使已删除数据重新对外可见。上线前另做适用法律与未成年人保护评估。

### P1-07：图控制权在 gateway 与 LangGraph 间分裂

- **类型/位置**：原文矛盾。§5，813、824、829 行；§6，917–923 行。
- **问题**：图边在 Python，却由 gateway 判断条件补问和 Critic 回跳；同时又要求 orchestrator 不回调 gateway。
- **建议**：orchestrator 统一裁决图边、缺项和循环；algo 返回规则/数值；llm-gateway 返回预算允许或拒绝；gateway 只转交命令和事件。调用预算与图循环是两层不同护栏，不能彼此替代。
- **验收**：gateway 重启不影响某个 run 的下一节点决策；同一图可用测试驱动完整执行，无需网关逐步指挥。

### P1-08：SSE 连接承担了任务生命周期

- **类型/位置**：设计缺口。原文 §5，815–833 行；§6，1012–1015 行。
- **问题**：断网后谁继续、谁落最终结果、如何补事件没有明确协议。当前 `StartGraph`/`ResumeGraph` 把命令与执行事件流耦合。
- **建议**：持久受理后返回 run；worker 独立执行；事件/结果先存后通知；SSE 只是可断开的订阅，另有状态/结果查询和显式取消。事件有 run 内序号，支持断点续订。
- **验收**：用户断网、gateway 重启、订阅多开，都不产生新 run 或丢失最终结果。未验证 token 不作为最终答案推送。

### P1-09：有检查点不等于有并发安全的执行权

- **类型/位置**：设计缺口。原文 §4，612–622 行；§12，1788 行；§15，2085–2092 行。
- **问题**：两个实例可能恢复同一检查点，重复调用模型、覆盖状态。Postgres saver 本身不提供全部业务互斥和计费幂等保证。
- **建议**：run 由带租约和 fencing epoch 的单执行者推进；关键提交校验执行权和状态版本；节点副作用记录稳定操作 ID。检查点存图进度，run 记录生命周期和执行权，两者关联但不混为一个概念。
- **验收**：旧 worker 租约失效后即使收到迟到 RPC 响应，也不能覆盖新执行者结果或发布终态。Redis 只能做可重建投影。

### P1-10：按 session 去重会吞掉合法的第二次回答

- **类型/位置**：原文协议缺陷。§6，1014–1015 行。
- **问题**：一次会话会有多次追问、确认和补问；`session_id` 既不是一次中断，也不是一次命令。
- **建议**：恢复命令携带 `run_id + interrupt_id + expected_state_version + Idempotency-Key`；确认再绑定 `profile_version`。同键同内容返回原回执，同键异内容或旧状态冲突；具体中断只能消费一次。
- **验收**：双击只推进一次，下一中断的新回答能正常受理；旧页面回答、越权恢复和并发矛盾回答均被拒绝。

### P1-11：缓存的 data_version 不是跨服务一致快照

- **类型/位置**：设计缺口，不是原文完全没考虑版本。§9，1424–1451 行；§7，1083–1114 行。
- **问题**：ETL 更新期间，候选、章程、规则和报告可能读到不同批数据；当前 schema 有 `data_version`，不代表实际查询受它约束。
- **建议**：暂存 → 质检/规则审核 → 原子发布 release 清单。run 绑定不可变清单，各读取端真正按版本选数据，禁止原地覆盖。清单区分计划、历史、一分一段、规则、文档索引及模型/算法配置版本。
- **验收**：中途发布新版本，原 run 不混读；重大错误撤销旧版本后，继续执行与最终发布均阻断。每次 resume 都校验，不等一小时。

### P1-12：硬预算缺原子预占及重试账本

- **类型/位置**：设计缺口。原文 §6，922–923 行；模型成本表与 §16 降级段。
- **问题**：并行调用同时检查余额会超支；图重试、网关重试、供应商重试叠加，实际尝试次数与账本不一致。
- **建议**：llm-gateway 调用前按模型价格、输入和输出上限原子预占，完成后结算。`logical_call_id` 标识一次语义调用，`attempt_id` 标识供应商尝试；重写报告是新的逻辑调用。超时但计费未知时保留未决预占并对账，不能立即释放再重复请求。
- **验收**：并发、超时、切模型和流中断下都不突破可预估预算边界；不声称供应商可保证 exactly-once 计费。早期若 Python 直连模型，只能标为无完整治理的实验链路，不作为正式保障。

### P1-13：画像修正后的回边与派生数据失效不一致

- **类型/位置**：原文矛盾。§5，818–824 行；§6，868–879 行。
- **问题**：补问文字说回确认，图线却进入策略；确认前换算位次，用户改分后没明确重算。
- **建议**：画像不可变版本化，确认绑定版本。首版采用保守规则：画像一变，全部下游产物失效；重新合法性校验、确认、候选/规则/证据/优化/报告。只对完全相同版本使用缓存。
- **验收**：600 分改成 580 分后，旧位次、候选、概率和报告均不能混入新结果。以后再按字段建立精细依赖，而不是一开始依赖复杂局部缓存。

### P1-14：原文算法流程与当前接口无法直接接合

- **类型/位置**：实现契约差距。原文 §5，825–830 行；§8，1303–1343 行；§10，1457–1559 行。
- **问题**：原文按“Strategy 选学校 → 约束 → 单独算概率”设计；当前 `EstimateProb` 是从成绩生成整池。原文还包含专业级概率、KDE、AdmissionSim 等当前未提供能力。
- **建议**：以已实现契约为基准：确认画像 → `EstimateProb` → 规则/证据与条件补问 → 策略偏好 → 必要的再次约束 → `OptimizeWishlist` → 可选 Critic → 报告验证。Strategy 不拥有候选身份和概率事实。
- **验收**：图节点读写字段逐个对上真实 RPC；只有位次的请求明确告知当前不支持，不能编造分数反推；`RankConvertReply` 没有控制线，也不能从中读取不存在的字段。

### P1-15：历史专业组数据不能直接作当年报考资格

- **类型/位置**：实现与产品承诺差距。原文 §8、§9；当前候选 SQL、选科校验。
- **问题**：上一年组内专业可能调整，当年仅检查组有计划不能证明某个专业仍招生。组级选科 match-any 也不意味着组内每个专业均可报；缺失学费映射为 0 不代表免费。
- **建议**：生产候选范围由当年计划形成，专业存在性与资格由当年规则裁决，历史记录只用于估算；需调整当前候选来源和资格过滤，不能只在旧过滤之后补一次新规则。专业组跨年沿用编码还需检测成员重大变化，标记可比性不足，不把代码相同当统计口径必然相同。无可靠历史的新组另列“无可靠估计”清单，不能静默漏报或编造概率送入当前优化接口。展示区分历史参考、当年事实与未知字段。
- **验收**：新增/撤销专业、重组专业组、部分专业受限和学费缺失等样例，不输出“全组可报”“保证录取某专业”“零学费”。无足够历史的新组应标无可靠估计，不伪造概率。

### P2-01：HITL 过期和恢复规则不自洽

- **类型/位置**：原文矛盾。§6，989–1006 行。
- **问题**：30 分钟过期，却一小时后才检查数据；过期既说检查点可恢复，又说重建会话。
- **建议**：过期的是 run，不是用户会话。过期 run 不原地恢复；可在同 session 派生新 run，重新确认画像和数据。人工等待与主动执行分别计时；检查点保留不等于仍有恢复权限。
- **验收**：过期边界、重复提交、跨年和版本撤销行为唯一且可测；具体推荐状态见第 6 节。

### P2-02：政策问答、方案解释、方案修改缺独立路由

- **类型/位置**：设计缺口。原文 §2，220–235 行；§6 全局必需字段表。
- **问题**：“某学校是否有语种要求”不一定需要成绩和完整选科；解释已有结果也不应自动重跑推荐。
- **建议**：同一 orchestrator 内设置 `POLICY_QA / GENERATE_PLAN / EXPLAIN_RESULT / REVISE_PLAN` 子图。问答仅收适用性必要信息；解释绑定既有结果；修改派生新 run。
- **验收**：普通政策问答不被迫交全套画像；问答结论若升级为“你可以报”，必须重新进入个性化资格流程。

### P2-03：概念 schema、脚本和契约草案混作实施规格

- **类型/位置**：文档及接线差距。原文 §9，1393–1405 行；§10，1457–1559 行。
- **问题**：原文使用 `college/admission_score/policy_doc/policy_chunk` 等，当前 schema 是 `university/major_admission/school_admission/charter_doc/charter_chunk`。检索验证脚本仍查询 `policy_chunk`。`track/category` 和 JSON 载荷也未完全收口。
- **建议**：第 9 节给出的映射应成为文档更新依据；在线接线前统一表/列和身份。把历史 proto 草案显式标为废弃，不与 `api/` 并列为权威契约。新增能力通过新 migration 和契约演进实现，不重放初始化脚本覆盖现有库。
- **验收**：干净环境的 schema、离线导入、在线检索使用同一套表和字段。这里只证明仓库文件不一致，没有检查实际数据库是否还保留旧表。

### P2-04：技术选择与性能成本的表述过度确定

- **类型/位置**：表述过强。原文 §4，489–499、558–560、612–622、669–691 行及成本估算段。
- **问题**：独立部署并不自动消除所有死锁；外置状态不自动等于随时重启安全；本地模型不是无成本；语言差异不能替代职责论证。SQL 的确定性也不代表源数据零误差。
- **建议**：保留当前技术选型，但改用可验证理由：部署/依赖隔离、团队熟悉度、批处理与资源管理、可复现性。价格、延迟、吞吐标测试日期、版本、硬件、并发和样本；区分目标 SLO、估算与实测。
- **验收**：报告不把一次热库耗时当 P99，不把算法测试通过当整个 Agent 系统已验收；观测上下文用标准传播，不仅靠字符串 `trace_id`。

## 5. 修订后的业务主线：先用现有算法形成最小闭环

### 5.1 可以直接复用的算法段

```text
已确认的合法画像
  → EstimateProb(province, year, category, batch, score, subjects, profile)
  → 得到 rush/stable/safe 三档 CandidateWithProb + AuditBasis
  → 合并为候选全集，保存组键、概率、依据，不让 LLM 覆盖
  → 应用已实现且明确的约束；新增条件能力需另行实现
  → OptimizeWishlist(candidates, profile)
  → 结构化志愿表 + 效用分解 + 保底/风险告警
```

`EstimateProb` 内部的真实调用顺序：
1. 校验上下文、配置、批次和选科。
2. `rank.Convert` 按省/年/科/分数取得位次和百分位；无数据明确失败。
3. `admission.LoadCandidates` 加载有当年计划的历史院校专业组及专业明细。
4. `CheckConstraints` 做选科过滤。
5. 批量读取历史组数据和计划数据。
6. `RecommendCandidates` 计算 `weighted_hit`、分档，并由 usecase 填充 `AuditBasis`。

这六步说明的是当前实现。正式推荐接入前仍需完成 P1-15：将候选成员和资格过滤对齐当年计划/规则，记录无法估计的新组及覆盖范围；不能把当前基于历史字段的选科过滤直接认作当年资格认证。

单独调用 `RankConvert` 只用于确认卡预览或独立位次功能，不是 `EstimateProb` 必须在外部先调用的依赖。若确认卡展示了推导位次，画像修改后必须重新预览；最终以同版本 `EstimateProb.basis` 为准。

当前 `EstimateProb` 不返回全部选科剔除清单；不能声称它已经提供完整的“为什么每个未入选学校都被拒绝”解释。独立 `CheckConstraints` 可对传入集合返回 kept/rejected，但这也不恢复已在候选生成阶段排除的所有记录。

### 5.2 最小产品闭环的边界

第一版不要求 Strategy/Critic 全开：结构化采集和确认 → algo → 模板报告 → 确定性核对即可形成可测试链路。LLM 首先用于自然语言解析及可核验解释。

在完整当年资格规则、版本和可靠执行尚未完成前，这只能定位为**受控算法演示/历史参考**，不能宣传“所有报考限制已核验”。输出需明确 `result_kind=ALGORITHM_PREVIEW`，把未覆盖条件列出，不允许导出成“资格已通过”的最终填报方案。

待第 4 节 P1 闭环完成后，才能按下一节到第 8 节的目标流程发布经过资格与事实校验的决策参考。任何结果仍不是代填或录取保证。

## 6. 目标身份、状态与执行模型

本节以及后续新增接口、字段、状态均为建议，当前仓库没有完整实现。

### 6.1 不同身份不得混用

| 身份/版本 | 含义与约束 |
|---|---|
| `principal_id` | 认证后的用户/受控匿名主体；由可信接入产生，不接受正文自称的身份 |
| `session_id` | 一段会话；可以包含多个生成、问答、解释或修改任务，不用它作为恢复幂等键 |
| `run_id` | 一次任务执行；每次方案修订创建新 run，并记录父结果 |
| `interrupt_id` | 某个 run 内一次具体人工中断；只能被一个合法命令消费 |
| `state_version` | 对外可见业务状态的乐观锁版本，不等于框架检查点编号 |
| `profile_version` | 不可变画像修订；确认只对这一版生效 |
| `release_id` | 本次任务绑定的数据/规则/索引发布清单，不是 ETL 运行编号 |
| `result_version` | session 内不可变的结果版本；解释、导出、修订都绑定它 |
| `event_seq` | run 内单调递增事件序号，供补发和客户端去重 |
| `logical_call_id / attempt_id` | 一次模型语义调用与实际供应商尝试；稳定操作身份避免重放时无限重计 |
| `lease_epoch` | worker 执行权代次；过时代次不能提交状态、检查点的有效指针或最终结果 |

当前 `algo.UserProfile` 只放风险、兴趣、城市、层次等效用偏好，不是完整考生画像。完整画像应另有运行时 schema，区分“未提供/不确定/拒绝提供/已确认”，记录字段来源；明确将 `track` 映射为 algo 的 `category`。完整画像中的硬学费上限、健康等字段不应悄悄塞进现有偏好 DTO 后声称已执行。

省年科批未明确的 INTAKE 阶段可暂不绑定 release，不能因此执行数据依赖节点；范围明确后绑定一次。绑定后画像变化只能在该清单仍覆盖新范围时继续重算，否则创建新 run 绑定新清单，不在同一 run 内静默换版本。

### 6.2 生命周期与节点阶段分开

```text
QUEUED → RUNNING → WAITING_HITL → QUEUED → RUNNING
            │           └──人工等待超时──> EXPIRED
            ├──验证及发布成功──> SUCCEEDED
            ├──不可恢复错误/执行超时──> FAILED
            └──显式取消──> CANCEL_REQUESTED → CANCELLED
QUEUED / WAITING_HITL 也可经 CANCEL_REQUESTED → CANCELLED
```

- `stage` 另记 INTAKE、PROFILE_CONFIRM、CANDIDATES、RULES、OPTIMIZE、REPORT、VERIFY 等节点阶段，不新增同名微服务。
- `SUCCEEDED` 说明任务完成，不说明“没有风险”。结果另带 `result_kind` 和资格/事实/保底状态。
- 未验证草稿不进入可查询的最终结果；`safe_guard_ok=false` 可形成带警示的已验证参考，但不能显示“安全达标”。
- `FAILED / CANCELLED / EXPIRED / SUCCEEDED` 均为终态；查看不改变它们。用户重试或修订创建新 run，保留关联，不复活旧终态。
- 终态竞争通过同一状态版本条件提交裁决：取消先提交，不能再发布成功；成功先提交，后到取消返回已经完成。

建议首版时限：一次 HITL 等待 30 分钟；主动执行累计上限 10 分钟（包含工具调用、重试及退避，不含人工等待）；模型单次尝试 30 秒且不得超过剩余任务时限。排队时间单独记录并设置容量/等待保护，不把排队耗时混作模型耗时。

循环计数保存在 run 中，画像修正或进程恢复不清零：信息补问共最多六次（INTAKE 与 BACKFILL 合计），Critic 方案修订最多两次，报告重写最多两次，验证发现硬错误后的上游回算最多两次。达到上限按对应错误出口结束，不把局部计数重置成无限循环；这些是建议值，不是当前图已实现的行为。

orchestrator 的恢复/超时调度器负责推进过期状态，不依赖 Redis TTL 回调。每次恢复和发布都检查 release 是否仍允许使用。过期检查点可暂留 7 天供排查或复制已授权输入，不能据此原地恢复；结果建议默认保留 30 天并支持提前清除，不默认永久保存。这些是初始工程建议，不是已批准的保留政策或合规结论。

### 6.3 最小可靠执行方案：PostgreSQL 即可起步

1. 命令受理在短事务中写 run/命令回执/初始事件，提交后才确认 accepted；gateway 超时重试使用同一幂等键。
2. orchestrator worker 原子领取 QUEUED run，取得租约和 epoch；网络调用期间不持有数据库事务或行锁。
3. 节点输入输出按稳定操作 ID 存储；大候选池、证据和报告作为不可变 artifact 保存，检查点保留引用，避免每一步复制整池到日志和状态。
4. 选定实际 LangGraph saver 及迁移方式；现有自定义 `plan_checkpoint` 表不能仅凭名字当成官方 saver 表。
5. 中断检查点先持久化，再让关联 `checkpoint_id` 的 interrupt/WAITING 状态对外可见；若两步无法共事务，增加幂等物化和恢复对账，不能先通知用户再丢失中断。
6. 恢复先原子消费中断并保存带 ID 的命令，再由 worker 应用；重放依据命令应用记录及检查点判断是否已执行，不能两次注入同一回答。
7. 节点完成、结果发布和事件序号分配都校验 epoch/状态版本。框架原始检查点也需按执行代次隔离或加存储护栏；只在 run 表加锁仍不足以防旧 worker 污染“最新检查点”。
8. run 状态与持久事件同事务提交或使用事务 outbox；通知只用来唤醒订阅，通知丢失后仍能从 PG 读回。
9. 租约失效后接管未完成任务；外部模型调用可能处于未知状态，先通过调用账本处理，不假设重复执行完全无副作用。

不需要现在引入 Kafka/Temporal。先验证上述故障恢复与并发语义，达到规模瓶颈后再考虑替换队列/调度实现。

## 7. 从用户请求到最终结果：逐步流程

### 7.1 阅读示例与前提

示例输入：“湖南，2025 年，物理类 600 分，选物理、化学、生物，偏好长沙，帮我做一份方案。”这里只展示字段流转，不引用具体学校、位次、概率或数量；报考年是用户提供，不是系统默认 2025 年。

前提：对应省年科批的数据和资格规则已发布且覆盖范围可证明；否则进入证据不足或算法预览，不执行正式推荐发布。以下 `SubmitRun/ResumeRun/WatchRun/GetRun/CancelRun` 均是建议接口，当前不存在。

### 7.2 主链路时序

```text
用户 → gateway：创建任务
       gateway → orchestrator.SubmitRun：可信身份、输入、幂等键
                    → PG：持久受理并返回 session_id/run_id
用户 ← gateway：accepted、状态/事件地址
用户 → gateway：订阅 SSE
       gateway → orchestrator.WatchRun：从指定 event_seq 订阅
worker → llm-gateway.Chat：解析意图/画像
worker → PG：保存画像；缺项/待确认时创建 interrupt
用户 ← SSE：问题或画像确认卡
用户 → gateway → orchestrator.ResumeRun：回答/确认具体 interrupt
worker → algo.EstimateProb：已确认成绩/省年科批/选科
worker ← algo：分档候选全集、概率、AuditBasis
worker → 规则评估 + RAG：当年资格/规则需求、文档证据
  如需条件补问：持久中断 → 回答 → 新画像版本 → 确认 → 重算
worker → algo.OptimizeWishlist：合法候选、已确认偏好
worker → 可选 Critic：受限修订，再优化
worker → 报告生成 → 三类证据校验 → 发布门禁
worker → PG：原子保存结果、SUCCEEDED、result 事件
用户 ← SSE / GET：同一个不可变结果版本
```

### 步骤 1：接入校验与可靠受理

- **谁调用谁**：客户端 `POST /v1/plans` → gateway → 建议的 `SubmitRun`。
- **输入**：用户文本、可选 session、幂等键；身份和追踪由接入补充，客户端不能指定任意他人的所有权。
- **工作**：gateway 校验大小/类型、鉴权、限流；orchestrator 核验可信调用方和会话归属，创建 QUEUED run。初始 release 可在明确业务范围后绑定。
- **持久化/返回**：在受控存储保存最小化后的可恢复输入、请求摘要、命令回执、任务身份、初始事件；不能只存 hash 导致 worker 无输入可恢复。返回 accepted 与查询/订阅地址，不承诺此刻已有方案。
- **失败出口**：未提交则无 accepted；提交后响应丢失，同幂等键查询或重试取回原 run，不能重复创建。

### 步骤 2：订阅与领取任务

- **谁调用谁**：客户端单独连 SSE；gateway 调 `WatchRun`。worker 独立从持久队列领取任务。
- **工作**：订阅端先补发序号之后的事件，再等待新事件；worker 取得执行权，将 QUEUED 改为 RUNNING/INTAKE。
- **持久化/返回**：保存租约和状态版本，推送不含敏感细节的进度。SSE 心跳不写业务事件，也不推进图。
- **失败出口**：订阅断开只关闭订阅；worker 失败由租约恢复处理；排队超载返回可重试状态，不无限积压。

### 步骤 3：意图路由与画像解析

- **谁调用谁**：orchestrator 本地路由逻辑；必要时调用 llm-gateway `Chat(role=profile)`，后者调用供应商。
- **输入/工作**：从用户已提供文本提取字段和任务意图；发送到云模型前先在受控环境做敏感字段最小化和脱敏。对用户主动写入的健康信息也不能原样整段转发；无法安全分离时改用结构化输入或本地处理。模型输出通过运行时 schema，不能猜省份、报考年、成绩或健康情况。含糊意图先澄清，不直接启动全部链路。
- **持久化/返回**：保存字段来源、未确认画像版本、使用量引用及缺项清单；省年科批完整后验证支持范围并绑定 release，缺项时进入补问，不强行选择数据版本。
- **失败出口**：模型不可用时可用结构化表单/固定问句；不存在对应数据或不支持的范围明确返回错误，不静默换年份/省份。

### 步骤 4：全局必要信息补问

- **谁调用谁**：orchestrator 的确定性完整性校验决定问什么；LLM 仅可润色问句。
- **工作**：校验省、年、科、批次、分数和选科；本科批可在产品明确限定并展示后采用默认。当前接口只有 score 输入，rank-only 不强行转换。
- **持久化/返回**：先保存中断检查点，再创建 INTAKE_ASK interrupt，进入 WAITING_HITL，发送问题、所需字段、回答 schema、版本和过期时间。
- **失败出口**：最多六次实际补问后仍缺关键字段，结束为 FAILED/INCOMPLETE_PROFILE；可提供另开政策问答的选项，不带缺项进入算法。

### 步骤 5：用户回答与原子恢复

- **谁调用谁**：客户端提交回答 → gateway → `ResumeRun`。
- **输入**：run、interrupt、期望状态版本、幂等键及强类型回答。包含确认时还带画像版本。
- **工作**：校验所有权、中断未过期/未消费、回答类型、状态/画像版本，以及已绑定 release 的有效性；尚未绑定的 INTAKE 只补输入。原子保存回答命令、消费中断、转 QUEUED。worker 再按检查点应用一次回答。
- **持久化/返回**：立即返回受理回执，不等待整图完成；worker 合并出新画像版本并重新校验。
- **失败出口**：旧 interrupt、同键异内容、并发矛盾提交返回冲突；同一命令重复返回原回执。EXPIRED 不恢复，建议创建关联新 run。

### 步骤 6：完整画像确认

- **谁调用谁**：orchestrator 进入 PROFILE_CONFIRM 中断，经事件流展示卡片。
- **工作**：展示实际采用的省年科批、分数、选科、软偏好/硬偏好区别和默认项。用户确认绑定 `profile_version`；修正则生成新版本，重新展示确认。
- **持久化/返回**：保存确认记录；确认成功恢复 RUNNING。可选位次预览调用 `RankConvert`，并绑定同一画像/release。
- **失败出口**：确认期间修改画像，旧确认失效；不从现有 `RankConvertReply` 读取不存在的控制线字段。

### 步骤 7：algo 生成权威候选池

- **谁调用谁**：orchestrator → `algo.EstimateProb`。
- **输入**：确认后的 province/year/category/batch/score/subjects，加现有偏好 DTO。目标设计还需传递并由查询执行 release 约束，不能只写入 trace。
- **工作**：复用第 5.1 节算法主链；正式推荐的前提是 P1-15 所述当年候选/资格口径已经补齐，未补齐时只运行算法预览。候选身份、概率、分档和依据都来自 algo，不允许 Strategy 替换它们；无法估计的组单独报告，不伪造概率参与优化。
- **持久化/返回**：保存候选全集 artifact、请求/响应摘要、画像与数据/算法配置版本、`AuditBasis`，进入 RULES 阶段。
- **失败出口**：缺一分一段/计划/历史、候选为空等按明确业务原因处理。只对瞬时传输故障在同输入版本内有限重试，不用旧年份兜底。

### 步骤 8：当年规则评估与证据检索

- **谁调用谁**：orchestrator 调用 algo 的扩展规则能力（待实现），同时调用本地 RAG 模块读已发布索引。
- **工作**：规则按当前目标候选给出 PASS/FAIL/UNKNOWN 和所需字段；RAG 按适用范围检索相关章程及政策，向量和全文两路的文档结果做 RRF/Rerank。SQL 数值结果不和 chunk 混成同一类 RRF 排名。
- **持久化/返回**：保存规则判定、覆盖信息、来源条款、待问字段以及文档证据 ID；分别维护合格、拒绝、待核实集合。
- **失败出口**：规则未知时不能仅靠 RAG 没搜到就 PASS；文档无可靠证据，删去相关非必要陈述或阻断依赖该事实的推荐。

### 步骤 9：按需条件补问与回算

- **谁调用谁**：orchestrator 根据规则需求创建 BACKFILL interrupt；用户仍经统一 `ResumeRun` 回答。
- **工作**：只问当前考虑候选确实需要的属性，合并相同问题；健康信息按最小粒度处理。用户拒绝/不知道，不等于条件满足，相关候选继续 UNKNOWN，用户可选择排除它们。
- **持久化/下一步**：回答形成新画像版本，返回 PROFILE_CONFIRM；按首版保守策略失效所有下游，重新生成候选及评估。不得直接跳到 Strategy。
- **失败出口**：新候选导致新补问仍计入同一 run 的补问上限；到上限可排除未知候选后重检可行性，不能绕过未知规则。若无可用候选，明确无法形成方案。

### 步骤 10：策略、偏好和候选范围确定

- **谁调用谁**：默认确定性逻辑；可选 orchestrator → llm-gateway `Chat(role=strategy)`。
- **工作**：Strategy 将自然语言偏好转为允许的参数或提出组键选择建议。软城市偏好交给效用排序；硬排除须已由用户确认。新增用户偏好必须回确认，不能由模型偷偷修改。
- **持久化/返回**：保存策略参数、来源和版本；验证所有组键属于同一权威候选池，数值与证据由服务端回填。
- **失败出口**：未知组键、篡改概率、未经确认的硬约束变更拒绝。千级候选不能全部塞给 LLM：保存全集，模型只看受控摘要；优化仍从完整合格集合取数，不能因 token 截断丢掉保底池。

### 步骤 11：约束复核与志愿表优化

- **谁调用谁**：orchestrator → 必要的 `CheckConstraints` → `OptimizeWishlist`。
- **工作**：当前 CheckConstraints 可复核选科并保持概率，扩展规则能力负责其他资格；没有输入变化时不必重复做同一轮选科计算。优化输入取自服务端合格池，不接收客户端/LLM 自造的完整候选事实。
- **输出/持久化**：保存排序后组列表、效用 breakdown/weights、`final_rank`、冲稳/稳拿保底数量、`safe_guard_ok`、近似滑档率及配置版本。
- **失败出口**：候选不足、保底不足分别表达；不得超出配置/当年规则数量上限硬凑。保底告警不转成“系统异常”，也不静默隐藏。

### 步骤 12：可选 Critic 与有界修订

- **谁调用谁**：orchestrator → llm-gateway `Chat(role=critic)`。
- **工作**：Critic 审查的是已经优化的实际方案，而非只看优化前候选；输出结构化问题，区分硬错误、事实错误、偏好权衡和一般建议。硬规则仍由代码复核，不由 Critic 定罪或豁免。
- **回边/持久化**：需要策略修订时回步骤 10/11；涉及新用户偏好则回确认。建议最多两次方案修订，按候选/参数摘要判断无进展后停止。
- **失败出口**：未解决硬错误不可继续发布；仅软偏好争议可以保留当前已验证方案及解释。Critic 是可选质量增强，不是最终门禁的替代品。

### 步骤 13：生成报告草稿

- **谁调用谁**：orchestrator 使用确定性模板，必要时调用 llm-gateway `Chat(role=report)`。
- **输入/工作**：仅提供最终结构化方案、脱敏规则结论、证据包、风险提示。模型生成解释，不重新排列最终志愿或改写算法数值；数字、名称和引用可由模板绑定。
- **持久化/返回**：保存未发布 draft artifact；对外只推“报告生成中”。首版不对外流未验证正文，避免用户把草稿当结论。
- **失败出口**：模型失败可尝试同输入的确定性报告模板，但模板也必须走下一步门禁；不能因为生成失败就省略关键限制。

### 步骤 14：三类证据校验与发布门禁

- **谁执行**：orchestrator 汇总校验；algo/确定性校验器检查数字和约束；可选 LLM 校验文本蕴含。
- **工作**：检查候选身份/去重/顺序、资格覆盖与 PASS、画像确认版本、release 有效性、所有关键数值与算法输出一致、引用存在且适用、派生结论未超出算法能力。
- **回边/持久化**：仅文案问题回步骤 13，最多两次重写；候选/资格错误回上游重新计算，消耗 run 级硬错误回算额度，不靠改措辞掩盖。保存逐条验证记录和失败原因。
- **失败出口**：预算/次数耗尽仍有关键错误，FAILED/VALIDATION_FAILED。只有同画像、同 release 下此前已通过完整门禁的不可变结果才可复用。

### 步骤 15：原子发布与最终呈现

- **谁执行**：orchestrator worker → PG；gateway 只读事件/结果转交用户。
- **工作**：短事务中再次检查租约、状态/画像版本、release 未撤销，保存不可变结果版本、验证摘要、SUCCEEDED 状态和 result 事件；避免取消与发布双成功。
- **返回**：SSE 给结果引用与摘要，GET 读取同一结果；断线用户重连可补事件或直接查询。用户确认/导出只是保存偏好和下载，不替用户提交真实志愿。
- **计费**：结果记录调用账本引用；仍未决的供应商费用显示待结算。计费投影后续更新不改写已发布方案正文。
- **失败出口**：事务未提交就不能对外宣告完成；事务已提交但推送失败，重放相同 result 事件，不重复生成方案。

## 8. 异常、修改与其他任务如何流转

### 8.1 常见异常与处理责任

| 场景 | 责任方与处理 | 明确禁止 |
|---|---|---|
| SSE 断网/刷新 | gateway 重建订阅，从 `Last-Event-ID` 对应序号继续；GET 为后备 | 因重连重新 SubmitRun、把断线等同取消 |
| gateway 重启 | 已受理 run 继续执行；新 gateway 重新鉴权后读取状态/事件 | 依赖原 gateway 才能落最终结果 |
| worker 崩溃 | orchestrator 租约到期接管，依据检查点/命令/调用账本恢复 | 两个执行者同时覆盖同一 run |
| HITL 双击 | 原子消费中断、幂等回执；同键异内容返回冲突 | 按整个 session 永久去重 |
| resume 响应丢失 | 同键重试得到原回执，查 run 当前状态 | 新造回答操作导致重复注入 |
| 模型 429/暂时不可用 | llm-gateway 统一有限尝试、退避与预算；上层复查同一逻辑调用 | 图、RPC、SDK 各自无限重试 |
| 模型超时且用量未知 | 保留未决预占、查询/对账；有足够预算且策略允许才新尝试 | 断言未调用成功所以一定不计费 |
| algo 参数非法/数据缺失 | orchestrator 提示修正或失败，使用结构化原因 | 换年份/省份、重试确定性非法输入 |
| RAG 无结果 | 重新措辞/通道尝试，保持适用条件；仍不足则证据不足 | 把零召回等同没有限制 |
| 数据新版本发布 | 旧 run 可继续用未撤销的不可变旧 release；最终结果注明版本 | 混读新计划、旧规则和旧向量索引 |
| release 被撤销 | 恢复/发布失败，提示新建修订 run；旧结果标记已过时 | 静默在旧 run 换数据却保留旧确认 |
| 人工等待到期 | run → EXPIRED，后续同 session 新 run | 原地复活终态或把 7 天保留当 7 天有效 |
| 预算耗尽 | 停止新模型调用；仅可用已验证结果/同门禁模板，否则失败 | 降级跳过资格或事实校验 |
| 用户取消 | CancelRun 原子记取消请求；worker 停止后续工作并转 CANCELLED | 保证已经发出的厂商调用一定撤回/免计费 |

重试建议：模型每个逻辑调用最多两次供应商尝试，具体 SDK 内部自动重试计入同一上限；algo 瞬时只读故障最多两次总尝试；所有尝试受统一剩余截止时间约束。格式错误导致的语义修正使用新逻辑调用并计入节点修订上限，不藏在网络重试里。

### 8.2 用户修改方案

1. 用户针对指定 `result_version` 提出“更保守”“不要某城市”或“成绩改了”。
2. gateway 鉴权后提交 REVISE_PLAN，orchestrator 在同 session 创建新 run，记录父结果版本，原结果保持不变。
3. 将修改提取为画像 patch，校验是软偏好还是硬要求，生成新 profile_version；原结果不是新版本的默认授权。
4. 首版统一使全部下游失效，重新确认后按步骤 7–15 执行；成绩、选科、报考范围变化尤其不得只重排旧池。
5. 新结果明确列出画像变化、版本变化与方案差异。未来只改软偏好时可以复用同 release 的候选池，但必须先实现依赖追踪和对应回归测试。

### 8.3 政策问答

1. POLICY_QA 只补齐问题所需的学校、报考年、省份/适用范围；与问题无关的成绩、健康信息不采集。
2. orchestrator 按发布版本调用 RAG；涉及精确招生人数/分数时使用领域查询能力。没有对应查询接口就明确补契约，不能假称当前四 RPC 已涵盖任意资料查询。
3. 生成带原文证据的答案并验证；无可靠资料回答“当前证据不足”，给出已核验来源的查询线索。
4. 输出政策解释，不自动推导“你有资格报考”。用户要求个性化资格判断时切换生成/资格流程并补齐必要信息。

### 8.4 方案解释

1. EXPLAIN_RESULT 读取用户有权访问的指定 result_version、当时画像/数据版本和验证记录。
2. 说明为什么排序、概率怎么估算、哪些限制或保底告警存在；不偷偷改变候选、权重或结果顺序。
3. 解释也走事实校验。若引用的发布版本已撤销，先提示结果过时；重新评估需创建 REVISE_PLAN。

## 9. 接口、表和证据包的具体收口建议

### 9.1 HTTP 与 gRPC 契约

以下是一套推荐命名，不是已有路由。保留当前 `/v1/plans` 作为兼容创建入口；旧 profile:confirm/backfill 可作为适配器转为同一恢复命令，不能各自再实现一套状态机。

| 对外入口（建议） | 内部 RPC（建议） | 关键语义 |
|---|---|---|
| `POST /v1/plans` | `SubmitRun` | 支持 task_kind、session、父结果引用和输入；持久受理返回 run |
| `POST /v1/runs/{run_id}:resume` | `ResumeRun` | interrupt_id、expected_state_version、profile_version、强类型回答、幂等键 |
| `GET /v1/runs/{run_id}` | `GetRun` | 生命周期、阶段、当前中断摘要、状态版本、错误及结果引用 |
| `GET /v1/runs/{run_id}/events` | `WatchRun` | SSE/gRPC 服务端流；按游标补发和等待，不启动图 |
| `GET /v1/runs/{run_id}/result` | `GetRun` 的结果读取能力 | 未完成返回明确状态；完成读取该 run 不可变结果 |
| `POST /v1/runs/{run_id}:cancel` | `CancelRun` | 幂等取消，终态保持稳定 |

命令回复只是“已受理”，不是“已执行完成”。所有查询、订阅、结果、取消也必须验证归属；`Trace.session_id` 不是鉴权凭证。浏览器 SSE 使用受控会话认证，不把长期访问令牌放进可记录 URL。

事件公共字段建议：`run_id / event_seq / type / stage / state_version / occurred_at / payload_version`；payload 使用 protobuf `oneof` 或有版本的运行时 schema，包含 progress、interrupt、result、error。当前 `GraphEvent` 只有 node/type/payload_json，缺这些恢复语义。

恢复回答建议区分：`AnswerFields`、`ConfirmProfile`、`RejectOrEditProfile`、`DeclineFields`。问句的人类文案与字段 key 分开，不通过自由文本猜测用户是在确认还是改分数。

客户端按事件序号去重；序号有缺口先补读，游标已超保留窗口时返回明确“需重新同步”，客户端 GET 当前状态。关闭 SSE 不保证收到终态，GET 始终可用。

llm-gateway 契约需补逻辑调用身份、预算作用域、prompt/schema/model 配置版本，以及流结束的 usage/cost/finish_reason/error。角色、模型、token 上限由服务端白名单限制；缓存命中可以不增加供应商费用，但仍记录逻辑调用和本地处理成本。

algo 契约演进需显式增加版本选择、资格扩展输入与 PASS/FAIL/UNKNOWN/所需字段；现有 `CheckConstraints` 缺报考年、健康等信息，不能承接完整规则。改 proto 时同步两端生成和契约测试；这是后续工作，本轮未改接口。

### 9.2 真实表映射与新增持久化责任

| 原文概念 | 当前仓库事实 | 建议 |
|---|---|---|
| college | `university` | 统一 school_id、招生代码、数据库 ID 的映射，不用学校名称作全局主键 |
| admission_score | `major_admission`、`school_admission` | 分专业录取和组投档数据；注明概率当前实际使用的来源与口径 |
| score_rank_map.track/rank | `category`、`cumulative_count` 等 | 文档/API映射与真实列一致，说明批次和百分位分母 |
| policy_doc/policy_chunk | schema 为 `charter_doc/charter_chunk`，脚本仍有旧名 | 接线前统一；若支持一般政策，显式扩展文档类型和适用范围 |
| Session | `chat_session` | 保留会话容器；run 承接一次执行，禁止一个 status 同时表示会话和任务 |
| LangGraph saver | 自定义 `plan_checkpoint` | 选定 saver 后编写兼容/迁移，不直接假设表可复用 |
| data_version | 只有版本登记等字段 | 增加实际不可变数据选择及 release 清单，不能只加缓存键 |
| LLM 记账 | `llm_call_log` | 扩展预占、结算、逻辑调用与供应商尝试，不依赖 token_used 事后累加 |

需要新增或扩展的逻辑记录：run、interrupt、命令幂等回执、执行租约、事件/outbox、画像版本、artifact/结果、数据发布清单、规则及审核记录、模型预占与 attempt 账本。它们可在现有 PostgreSQL 中实现，不意味着每项都要一个服务。

当前 schema 中部分招生表唯一约束未包含 province，major 基础表也没有年/省适用域；在湖南单省范围内应明确边界，扩省前必须核对身份和唯一键，不能直接复用现有键宣称支持全国。

### 9.3 三类证据包

| 类型 | 至少保存 | 如何验证 |
|---|---|---|
| 文档事实 | 文档/片段 ID、标题、来源、适用范围、生效区间、原文摘录/位置、内容摘要、release | 引用存在且未变、适用性匹配、原文支持陈述；语义无法确定则标待核实 |
| 结构化事实 | 表/数据集、业务键、字段、值、单位、来源年份、release | 与同版本权威行/快照逐字段比较，不让模型口算或补值 |
| 算法派生事实 | 输入和候选快照、有效样本、方法、配置/代码版本、输出、假设及告警 | 确定性重算或与已保存输出一致性比较；核验展示精度，不与章程原文硬比概率 |

`AuditBasis` 是现有基础，不是完整证据包：还需实际数据发布版本、配置、有效样本和输入输出身份。目标“可复现”需要同时固定数据和算法参数，仅记录方法名或当前 Git 分支不够。

### 9.4 离线发布流程

```text
原始公共资料
 → 暂存导入及来源/身份映射
 → 结构化质量检查、异常与跨年组变更识别
 → 条款抽取（可辅助）→ 规则人工审核/冲突处理
 → 切分、Embedding、全文索引、检索评测
 → 结构化/规则/索引覆盖及回归全部通过
 → 原子发布 release 清单
 → 在线 run 绑定并只读；严重错误撤销对应 release
```

版本落地要求：给数据/规则/索引实际加入版本维度或使用不可变快照，并让每条查询选到对应版本；只在 session 存一个整数无效。不把数据库事务跨越 HITL 长时间保持打开。普通新版本不自动破坏旧运行，安全撤销则阻断旧版继续发布。

文档检索还需验证中文全文分词和召回质量，存在 tsvector/GIN 不等于关键词检索已可用。Embedding 与索引必须记录模型/维度版本，模型更换不能复用不兼容向量。检索文档按不可信数据处理，里面的指令不能覆盖系统规则、授予工具权限或更改预算。

## 10. 推荐实施顺序与验收清单

### 10.1 按可运行增量推进

| 顺序 | 工作包 | 完成条件 |
|---|---|---|
| A：规格对齐 | 更新主链、当前能力标签、画像/任务/事件 schema、发布门禁及支持范围 | 流程每步能映射到已有接口或明确新增契约；本报告建议经确认后再实施 |
| B：可靠任务底座 | 持久受理、worker、真实 interrupt/checkpointer、恢复幂等、SSE/GET/取消 | 不调用真实付费模型也能用测试替身通过断网、崩溃和并发恢复测试 |
| C：算法最小闭环 | 接入现有四 RPC、确认画像、结构化结果、模板校验 | 完成受控 ALGORITHM_PREVIEW；不得宣称全部资格已核验 |
| D：生产资格与证据 | 当年规则链、数据版本读取、RAG、三类证据、隐私删除 | 未知资格/错版本/错引用不能通过正式方案发布门禁 |
| E：模型治理与表达 | llm-gateway 预占/结算、受控画像解析及报告生成、失败模板 | 并行/超时/供应商失败预算可核对，报告不能改写数值和资格 |
| F：智能增强 | Strategy、Critic、政策问答、解释/修订子图及性能评测 | 在已有门禁之上有可测收益，循环有限且不降低可靠性 |

若 B/C 阶段就接真实模型，必须提前完成 E 中的最低预算、隐私和调用账本能力；不得因表格顺序把治理延后到已有真实流量之后。正式推荐发布要求相关 P1 一并通过，不以完成某个工作包单独代表可上线。

### 10.2 关键验收场景

| 编号 | 测试输入/故障 | 必须观察到的结果 |
|---|---|---|
| T01 | 合法且规则资料完备的省年科批画像 | 候选/概率来自 algo；完整确认、验证、发布及 GET/SSE 一致 |
| T02 | 缺成绩/省份，连续六次未补齐 | 不进入算法；返回关键字段不足，无伪完成结果 |
| T03 | 只给位次，现有接口未扩展 | 明确能力边界，不反向编造分数 |
| T04 | 同一确认双击、两个标签页不同回答 | 相同命令一次生效；冲突回答被拒；下一次合法中断可继续 |
| T05 | 中断持久化前后、回答提交后分别崩溃 | 不出现“已通知但无检查点”或重复应用回答 |
| T06 | worker 在模型请求后崩溃、另实例接管 | 旧 epoch 不能发布；账本保留未知计费，不无限重试 |
| T07 | 用户在计算/发布过程中断网或重启 gateway | run 独立完成；订阅补发或 GET 得到同一结果 |
| T08 | 多个模型调用同时接近预算上限 | 原子预占限制总额；账本可区分语义调用和供应商尝试 |
| T09 | 600 分确认后改成 580 分 | 新 profile_version；旧位次/候选/证据/报告均失效 |
| T10 | 执行中发布新数据或撤销旧 release | 普通更新不混读；撤销阻断恢复和发布，并提示重新生成 |
| T11 | 章程零召回、规则缺失、体检未知 | 分别标明原因；不能推断无限制或资格通过 |
| T12 | 组内部分专业受限、组成员跨年变化 | 不声称全组专业可报；标记历史可比性与当年资格范围 |
| T13 | 报告数字被改、引用错学校/年份 | 数值/适用性校验阻断；达到重写上限仍不能发布 |
| T14 | 保底不足但资格和事实通过 | 正常结构化结果带醒目风险告警，不伪报 safe_guard_ok=true |
| T15 | 取消与最终发布同时发生 | 仅一个合法终态；已发送厂商调用费用仍可结算 |
| T16 | 非所有者查询/订阅/恢复/取消 | 全部拒绝，不能靠猜 run_id 读出画像 |
| T17 | 政策问答、解释已有结果、修改偏好 | 各走对应子图；问答不收无关成绩，解释不悄悄重算 |
| T18 | 用户删除数据、日志/缓存检查、备份恢复演练 | 敏感数据不进入不必要系统，删除策略贯穿派生数据 |
| T19 | 全量候选很大、模型上下文被限制 | 权威全集仍保存，优化不因 prompt 截断失去保底候选 |
| T20 | 模型调用不可用或预算不足 | 仅返回经过同门禁的模板/既有结果，否则明确失败 |

测试应分纯状态/规则单测、跨服务契约测试、受控故障注入、真实数据回归和上线前隐私/安全检查；不必每次单测调用付费模型。观测同时统计主动执行时间、人工等待、排队、节点重试、预算预占/结算、未知资格和门禁拒绝率。

## 12. 审查结论的适用边界

- 本报告给出了明确推荐设计，但不是已实施说明；原文与代码的修改需要另行开展。
- 对 schema 的判断来自仓库文件，不推断当前数据库已执行哪些 migration 或保留哪些旧表。
- 当前算法的功能与限制来自实际用例/接口，不把 proto 超前注释当实现，不将历史测试结果当本轮重新验证。
- 未进行浏览器体验、线上容量、安全认证、规则法律适用性或录取概率校准验证；这些仍需专项验收。

最终建议：**保留四服务及确定性算法基础，让 orchestrator 成为唯一流程所有者，让任务脱离连接独立存活，让每次推荐绑定已确认画像和一致数据版本，再以资格与证据门禁控制所有成功出口。** 这比增加 Agent 数量更能提高正确性、可维护性与可恢复性。
